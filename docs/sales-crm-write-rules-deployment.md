# Sales & CRM write rules: deployment guide (owner-run)

Migration `supabase/migrations/20261222000100_crm_sales_write_rules.sql`, owner pack `supabase/manual-sql/crm_salesfix_*`. **Status, dated.** When this guide was written (2026-11-08) nothing had been applied to any hosted project. **Update 2026-11-09 (owner-run verification, owner-reported):** the owner applied the migration on hosted V2; the before and after snapshots differed only in the seven intended entries and all 18 read-only verification checks passed (see "Hosted V2 result" at the end). Claude ran no hosted SQL and did not see the result rows. Everything below was rehearsed by Claude only on a throwaway local database (RLS suite `packages/rls-tests/test/crm-sales-write-rules.rls.test.ts`) and the isolated local stack (`apps/web/os-shell-checks/sales-crm-readiness-flow.mjs`). The migration is additive and idempotent (`create or replace`), **changes no stored row**, and edits no applied migration.

## What it changes (three database rules, plus decision B)

| Rule | Before | After |
|---|---|---|
| **Zoho Books references** (`crm_upsert_zoho_reference`) | Overwrote every field with what the form sent: a stale form, or two people editing different fields at the same time, lost data; a blank could not be told apart from "not sent" | New `crm_save_zoho_reference(opportunity, fields jsonb, expected jsonb)` (pattern of `proj_save_handover`): a key that is **present** is set (JSON null or blank = an intentional clear), a key that is **absent** keeps the stored value. The opportunity row is locked first, so two saves apply one after the other and the second merges into the first's result. `expected` carries the value the person saw for each field they changed; if that field changed meanwhile the save is refused at once (SQLSTATE `23514`, "Someone else changed the quote reference since you opened this form..."; not `40001`, which PostgREST retries until the call times out). A **Lost** enquiry's references are read-only (the screen already hid the form on Lost; every sibling function refuses a closed enquiry); Won stays editable (invoice and payment references follow a win). **Owner decision B (see below): an existing quote reference cannot be cleared once the enquiry has reached Quote sent.** The old 7-argument `crm_upsert_zoho_reference` is **kept with the same grants** and now delegates: a NULL argument means "leave as it is" |
| **Proposal superseding** (`crm_set_proposal_status`) | `superseded` was accepted from any starting status (an accepted version could be superseded by a direct call) | `superseded` is allowed only from `draft` or `sent` (what `crm_quote_issue` supersedes and the only statuses the proposals panel offers); `accepted` and already `superseded` are refused (`23514`). The proposal is re-read after the opportunity lock, so a concurrent "accepted" cannot be overwritten. The `sent` and `accepted` rules, the closed-enquiry rule and the estimate-sent guard (`EST01`, trigger `crm_proposals_estimate_sent_guard`) are untouched |
| **Won evidence date** (`crm_mark_won`) | The no-future-date rule existed only in the form | A date after `crm_today_dubai()` is refused (`22023`) before any write. Boundary: the **Dubai calendar day**, exactly the form's `max` (`todayInDubai()`); today is accepted. A refused call leaves the enquiry (stage, version, columns), `crm_closures`, follow-ups, the handover row and the timeline unchanged. Stored Won rows are not touched |

## Owner decision B: the quote reference cannot be cleared once the enquiry has reached Quote sent

The gate that moves an enquiry to Quote sent (`crm_move_stage`) is checked only at the moment of the move, so before this change a person who may edit could empty the quote reference at any stage. The owner decided (option B): **an existing, non-blank Zoho quote reference cannot be cleared (set to empty or blank) once the enquiry has reached Quote sent.** It is the evidence that unlocked the stage.

* **Stages (the real values of `crm_opportunities.stage`, migration `20261115000100`):** `quote_sent` (Quote sent), `negotiation` (Negotiation) and `won` (Won). An enquiry **On hold** (`on_hold`) that was put on hold **from** Quote sent or Negotiation (`stage_before_hold`) is protected too, so the rule cannot be bypassed by holding, clearing and resuming. Clearing at New, Qualified, Proposal prep and Proposal sent, and on hold from those, behaves as before.
* **Refused:** clearing the quote reference (JSON null, empty or blank) when it currently holds a value, at those stages. SQLSTATE `23514` (not `40001`, which PostgREST retries), message: "The Zoho Books quote reference cannot be cleared once the enquiry has reached Quote sent (Quote sent, Negotiation, Won, or on hold from one of them). Replace it with the correct reference instead." The whole save is refused, so nothing else in it is written. The app shows this message as it is.
* **Allowed:** correcting to ANOTHER non-blank reference at those stages (also re-sending the same one); changing any other field, including the invoice and payment fields on **Won** (they stay editable and clearable); a save that omits the quote reference; a first non-blank reference on a record that has none.
* **Existing records with a MISSING quote reference** at those stages are **not backfilled and not blocked**: the migration changes no row, and an edit that does not touch the quote reference, or that sets a first value, works on them as before (the preflight reports them, see step 1).
* **Lost** stays read-only (every save refused with the read-only message, also one that would clear).
* **Where it is enforced (every write path):** (1) `crm_save_zoho_reference` (clear message, nothing written); (2) the old signature `crm_upsert_zoho_reference`, which delegates to it, so a call with an empty string (`''`) is refused at those stages too; (3) a `BEFORE UPDATE OF quote_ref` row trigger `crm_zoho_quote_ref_guard` on `crm_zoho_references` as the backstop for any other statement or function (the table owner or an administrator). No other function writes the table (checked in the RLS suite by scanning every function body), and signed-in users have SELECT only on it (no insert, update or delete policy). The two helpers (`crm_zoho_quote_ref_protected`, `crm_zoho_quote_ref_guard`) are internal: nobody can call them. Deleting the row is not exposed to anyone (only the enquiry's deletion cascades).
* **The Quote sent gate itself is unchanged** (a non-blank quote reference is needed to move to Quote sent). One step back to Proposal sent is an existing rule; the reference may then be cleared there, and the gate asks for one again before Quote sent.

## Release order with the app: database first

**The migration AND its verification (steps 1 to 5 above: preflight, preservation check, migration, preservation check again, verify) must be COMPLETE before staff use Zoho editing in the new app.**

The new app has **no fallback**. It saves Zoho references only through `crm_save_zoho_reference`. If that function is not installed (PostgREST `PGRST202` / Postgres `42883`), the save is **not attempted any other way**: the form shows "Saving Zoho Books references is temporarily unavailable ... nothing was saved. Trying again will not help until a required database update is installed", the stored references stay **readable** on the page (reading does not use the function), and the message is different from a validation refusal ("cannot be cleared", "amount must be zero or more") and from a stale-edit refusal ("Someone else changed ..."). **So with the new app and the OLD database, Zoho saving is unavailable by design.** Everything else in the app (including the Won date limit and the supersede button rules) works against either database.

* **Recommended: database first.** Apply and verify the migration (steps 1 to 5), then deploy the new app. Right after step 3 the database cache may need a few seconds before the new function is visible; the verify step is complete only when all 18 rows say OK.
* **App first** is acceptable **only if staff do not edit Zoho references until the database steps are done**, because until then every save in the new app answers "temporarily unavailable".
* **If the migration is rolled back** (pack step `90`), the new app returns to the "temporarily unavailable" state for Zoho saving until the migration is applied again.

## Cutover: the OLD app against the MIGRATED database (checked, residual risk)

After step 3 and before the new app is live, the OLD app still calls the old 7-argument `crm_upsert_zoho_reference`, which the migration keeps as a compatibility function (same grants). What it does now, **reproduced in the RLS suite** (`1c. The OLD app against the MIGRATED database`):

* **It can overwrite another person's concurrent edit.** The old form sends every field it loaded, with the values it loaded; every non-blank value is applied. If Sara opened the old form, a founder then corrected the invoice reference, and Sara saves (changing only the quote sent date), the old call carries Sara's old invoice reference and **replaces the founder's correction**. The old function has no version or seen-value, so the database cannot tell a stale value from a deliberate one. This is the original problem and it **cannot be fixed for the old app**.
* **It cannot clear a field.** The old app sends NULL for an emptied field, and through the compatibility function NULL means "leave as it is": the person sees "saved", the value stays. (Called directly with an empty string `''` the old signature does clear a text field, but only below Quote sent: decision B applies to it too.)
* It cannot get around decision B (clearing the quote reference at Quote sent, Negotiation or Won is refused for the old signature too) and its permission rules are unchanged.

**How to avoid the risk during cutover (do this):**

1. **Brief Zoho-editing freeze.** Tell Sales not to edit Zoho references between applying the migration (step 3) and the new app going live. Owners and founders are the only people who can edit them.
2. **Or deploy the new app immediately after the migration** (the window is then minutes). Sales then uses the new form, which sends only changed fields with the values seen, refuses a stale edit of the same field and never overwrites a colleague's other fields.
3. **Everyone with a Sales enquiry open during the cutover must refresh the page (hard reload, Ctrl+Shift+R / Cmd+Shift+R)** once the new app is live. A stale old form in an old tab can still overwrite as described above.

**Options not implemented** (reported, not trivially safe): (a) a version or timestamp guard in the compatibility function is not possible without changing the old app, because the old call carries no seen-value or version; (b) after the new app has been live for a while and old tabs are gone, a later migration can revoke execute on the old 7-argument function, so any leftover old tab fails loudly instead of overwriting silently. Until then this is a **documented residual risk**, limited to the cutover window.
