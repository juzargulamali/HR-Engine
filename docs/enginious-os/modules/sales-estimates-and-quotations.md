|---|---|---|

A proposal row holds only a note and a file, so it cannot hold sections, lines, currency, VAT, bill-to, milestones or terms | migration header; `crm_quote_create` |

| Withdraw / cancel | The existing model: "Mark superseded" on Proposals & files (`crm_set_proposal_status`). The snapshot is never altered | proposal status model |
| Approval (bound to the exact version) | Existing commercial approval, now tied to a content hash (`crm_quote_content_hash`: everything client-facing, never internal notes). ### 2.2 Estimate page: three steps (`.../quotations/[proposalId]/page.tsx`, `editor.tsx`, `lib/crm/quotations/builder-state.ts`)

**One draft per estimate, saved as the person works.** One working copy, a bar that is always visible with the running totals, the save state, a **Save draft** button (still there, for people who want to press it) and Back / Next.

*When it saves.* About 0.8 seconds after the last keystroke or change (details, notes, items), and at once when the person adds a section, attaches a photo, presses Save draft or presses Finalise / Request approval. Every change to the saved draft goes through ONE queue on the screen (`lib/crm/quotations/save-queue.ts`): saves run one at a time, asks made while a save is waiting are folded into it, and an ask made while a save is running queues exactly one more that includes what was typed meanwhile. Section adds, photo attaches, item deletes, moves and the finish run in order with the saves, so two overlapping saves can never create a second copy of an item or a section. An item keeps its screen key when it gets its saved id (no remount, no lost cursor), and what counts as saved is what was SENT, so an edit typed while a save runs is still saved by the next run.

*What the person sees.* "Changes are saved automatically" (nothing typed yet), "Saving…", "Saved" (only when every write succeeded), "Not saved yet" with the item and the reason (an item that cannot be saved as typed, for example no quantity, stays on screen and is left out of the automatic save until it is complete), and "Could not save" with the reason when a write failed: what was typed stays on screen and is saved again on the next edit or on **Save draft**. Items already written keep their ids, so retrying cannot duplicate them. Leaving with anything unsaved asks first.

### 2.5 Frozen snapshot (the seam for the exports)

`crm_quotation_snapshots.content` (type `QuotationSnapshot`, `packages/domain/src/quotations.ts`): `schema_version` (1), `reference`, `revision`, `issue_date`, `validity_date`, `enquiry`, `issuer`, `bill_to`, `currency`, `vat`, `sections[]`, `totals`, `milestones`, `exclusions`, `terms`. For an estimate, `terms.label` is the format marker (`estimate-format:1`) and `terms.clauses` holds only the Assumptions and Next steps clauses; the notice is not stored: it is printed from the domain constant of the marker's version, so the wording a document was finalised under is the wording it re-exports with. Guard triggers refuse any change, even by a table owner. Read it through `loadQuotation(...).snapshot` (`apps/web/src/lib/crm/quotations/data.ts`).

## 3. Not covered (stated, not hidden)

No costing, supplier price, margin or discount. No sending of an estimate (staff download and share the files themselves). Moving an item to another section: delete and re-add. Hiding or editing an existing VAT choice has a database function but no screen. The photo upload cannot be driven on the local stack (no object storage). New estimates still carry a `QUO-` reference (section 0). The database still lets the enquiry owner or a founder record an estimate row as sent by calling `crm_set_proposal_status` directly (the app refuses it). Notices in the Excel sheet and the PDF use the constant of the format version, so a change of wording needs a new version number.
