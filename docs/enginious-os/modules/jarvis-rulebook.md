# The Enginious OS rulebook for JARVIS

What JARVIS may do, for whom, with which records, what it may show, what may leave Enginious OS for the AI provider (Anthropic), and what needs a confirmation. **This document and the code are kept in step by a test**: the enforced copy is `apps/web/src/lib/jarvis/rulebook.ts`; `apps/web/src/lib/jarvis/assistant-rules.test.ts` fails if a capability below is missing here, if a registered action has no rule, or if an action could call the provider without its rule approving it. To change a rule, change both in the same pull request.

Related: how JARVIS works [`jarvis.md`](./jarvis.md); the Sales actions [`sales-action-catalogue.md`](./sales-action-catalogue.md) section 3.9; the staff guidance JARVIS answers from [`../staff-guidance/README.md`](../staff-guidance/README.md).

## 1. Principles (each is enforced on the server)

1. **Deny by default.** A capability, a field or an outbound source that is not listed in section 2 is not approved. Unknown action ids are refused by the registry (`lib/jarvis/registry.ts`); a provider request from a capability without an approving rule, or with a source its rule does not list, is refused by the outbound gate (`lib/jarvis/outbound.ts`).
2. **The signed-in person's identity, every time.** Every request, every lookup and every follow-up is authorised again from the session (`createDispatcher.authorize`, `lib/jarvis/dispatcher.ts`): JARVIS switched on, the person on the pilot list, the company allowed, the module grant for the selected company; then the action's own rule; and the records are read through that person's own database session, so the database's company and record rules decide what exists for them. There is no privileged database client in JARVIS.
3. **Nothing is proof of permission except that check.** Not the model, not a prompt, not memory, not an earlier answer and not the context the browser sends with a follow-up. "Show last month instead" runs the lookup again; if access was removed in between, it is refused.
4. **The model never decides.** Messages are routed locally by fixed rules (`lib/jarvis/router.ts`); no provider call classifies intent. The model can only return a proposal or a text; it has no tool that reads or writes anything.
5. **Writes need the person's confirmation** on a review card, bound to the reviewed values and verified in the database (`jarvis.md` section 6). A chat message such as "confirmed" saves nothing. A repeated confirmation returns the original result.
6. **JARVIS sends no messages.** A draft is text for the person to review and copy.
7. **Provenance decides what may go to Anthropic** (section 3): what the person supplies for a task may go as written, working financial figures included; operational data Enginious OS holds may go only as typed fact lines and locally screened record text for the capabilities that name those sources; **financial information Enginious OS holds never goes**, and genuinely restricted material stays inside whoever supplies it.

## 3. What may leave Enginious OS, and what may not

**The rule is provenance: where the information came from, not whether a number appears in it.** (Owner decision, 2026-11-11; it replaces the earlier rule that nothing Enginious OS holds may be attached and that internal costs may not be pasted.)

| Kind | Rule |
|---|---|
| **A. What the person deliberately supplies for the current task** (typed or pasted): Sales context such as project and company names, the client, agency and end client, contact names, venue, dates, game journey, technical requirements, quantities, **and working financial figures: proposed values, budgets, prices, unit rates, costs, margins on a working estimate** | **Allowed** to go to Anthropic for that task, as written. They are the person's assumptions, not verified facts: the model is told never to present one as a recorded or confirmed value. The panel says so next to the input. A supplied figure is used for that task and its direct continuation in the same general conversation (at most four earlier turns); it is never stored as memory and never copied into another Sales task |
| **B1. Operational data Enginious OS holds** about Sales records the requester can see: company, client, agency, end-client and event names; enquiry reference and title; stage; dates; ownership as "you" or "another owner"; follow-up titles and due dates; activity dates; non-financial counts, quantities and count-based shares; screened enquiry descriptions, scope, meeting notes and recorded non-financial reasons | **May go, only as two typed sources** and only for the capabilities whose row in section 2 names them: `sales_facts` (fact lines built field by field in `sales/projection.ts`, `sales/summary.ts`, `sales/scope-draft.ts`) and `sales_record_text` (free text of one record after `redactAppText` removed every sentence with a financial figure or restricted material). They travel in their own request fields, which only server code fills; the gate screens them under the "app" rule and refuses them for any capability that does not list the source. There is no generic "record" source. Email addresses and phone numbers are not projected |
| **B2. Financial information Enginious OS holds**: enquiry or project values, currency amounts, budget notes, payment terms, prices, unit rates, estimates, quotations and proposals, costs, margins, discounts, tax, turnover, revenue, profit, expenses, any financial aggregate or derived financial metric; **and any financial figure inside a stored title, note, scope or meeting text**; prepared estimate documents, saved estimate content, attachments, files and document links | **Never goes**, even for a person allowed to see it and even when they ask JARVIS to fetch it. No projection selects a financial column (a test checks every column list); a figure inside stored free text is removed locally or the text is omitted; the gate refuses any app-held part that still carries one. It stays in the authorised screens and forms, where JARVIS links to it. A user edit, a confirmation or a source label cannot change this |
| **C. Genuinely restricted material, whoever supplies it**: employee documents, salaries and payroll, reimbursements, medical and insurance records, private leave details, personal IDs and bank details, credentials, company financial statements, ledgers and company results (turnover, profit, valuation), a pasted prepared estimate or quotation document (its number and totals), embedded files, and anything marked as not for external sharing | **Stays inside Enginious OS.** It is screened out before any provider call and in every answer. JARVIS does not show or discuss it; it points an authorised person to the screen |

**What survives, by design:** non-financial numbers. Two counters, six products per counter, an RTX 4070, 18 to 20 May 2027, a 55-inch screen, 1,200 wristbands and counts of enquiries all go through, in the person's text and in app-held facts.

How C is enforced, in layers (a word list alone would not be enough, so it is only the last layer):

1. **Declared sources and structural provenance.** Every provider request states what it is built from and the gate (`lib/jarvis/outbound.ts`) refuses a source the capability's rule does not list. What the person supplied is in the request's `input`; what Enginious OS holds can only be in `facts` (typed lines: a fixed label written in the code, and a value that is a whole number, a date, a name or a screened title) or `recordText`. A request that carries one of those fields without its source, or the source without the field, is refused; so is a decimal or very large number as a "count", and a label that carries digits. The browser cannot fill these fields, so a label saying "user text" cannot move stored data across.
2. **A sharing restriction is enforced at the common boundary.** A text marked as not for external sharing ("External sharing prohibited", "Internal use only" and its variants such as "internal-only" and "for internal use", "NDA", "Confidential", "Do not forward") makes no provider call **in any capability**: the gate refuses it whichever mode was chosen (enquiry, Sales reply, update, meeting notes, general chat), whether the text was edited, and whether the marking is in the message or in the earlier context (`wholeTextRestricted`). The person is told in words and, for an enquiry, pointed to the new-enquiry form. An ordinary sentence that merely contains such a word ("parking is restricted") is not a marking.
3. **Screening of everything that goes out, by origin** (`findProtectedContent(text, origin)`, `lib/jarvis/protected.ts`): the person's text and the earlier general-chat turns under the "user" rule (working figures allowed; kind C refused); every fact value and every line of record text under the "app" rule, where **any** financial figure is refused (a currency amount, or a financial word such as price, rate, budget, cost, value, quote, estimate, discount, margin, payment or total next to a number or a percentage). If something restricted is found, or the request is too long or contains an embedded file, **nothing is sent**. The provider is never asked to redact anything.
4. **Screening of what comes back.** A model answer that contains restricted material is withheld. The wording of a summary is checked against the figures it was given: a number that is not among them, any amount of money, or (for a period) a claim of delivery drops the wording and the card shows the app's figures alone. A line of a scope draft that carries an amount is dropped. A generated figure is never used as a stored value or in a calculation. A lookup's free text is screened before display and restricted personal data is replaced by "Details hidden here. Open the record to see them."
5. **Logs are blind.** Only event names, capability ids, outcome codes and durations are logged; never text, values, provider payloads or chat.
6. **This release is pasted text only.** No file is uploaded to Anthropic.

### 3.1 An enquiry brief

Decided **locally, before any provider call** (`apps/web/src/lib/jarvis/sales/brief-outbound.ts`). The model is never relied on to remove anything.

| In the brief | What happens |
|---|---|
| The Sales context of kind A, including quoted prices, unit rates and client budgets | Sent as written. Nothing is summarised, stripped or cut |
| A restriction on the **whole** brief: "External sharing prohibited", "Internal use only", "NDA", "Confidential", "Do not share", "Restricted", "Embargoed", "Privileged", in the heading (first three lines), as a short notice line, or said of the brief itself | **Zero provider calls, in any version.** The editable preview is not offered and an edited text is refused: it cannot lift the restriction. The person is pointed to the new-enquiry form |
| Restricted material of kind C mixed into an otherwise usable brief | The brief is **not sent automatically**. The panel shows a clean excerpt (the brief without those sentences) for the person to check, edit and send, with the new-enquiry form as the other way. Restricted text put back into the edited version is refused again |
| Email addresses and phone numbers | Replaced by `[contact withheld]` (not needed to prepare an enquiry). A budget range such as "AED 50000-65000", an amount or a date is not a phone number and is left as written |

**What the model reads is separate from what the app saves.**

| On the review card | Comes from |
|---|---|
| Client, end client and agency | The labelled lines of the brief, read by Enginious OS and matched to organisations the person can see. "Client" next to an "End client" is the agency field; alone it is the end client. The model's answer does not override a labelled name |
| Value and currency | **Only one clearly stated client budget** ("Client budget: AED 85,000", "the client's budget is ..."). A range, an approximate figure, conflicting values, an internal figure or a budget not said to be the client's leave the numbers **blank**. The model's figures are never used |
| Budget note | The original wording of the budget, for the reviewer (an internal figure is not copied) |
| Brief | **The model's summary, when it is one**: a concise factual project brief (no instruction to JARVIS, greeting, signature, unrelated lead or obsolete detail). The pasted text handed back is not accepted as a summary, and a summary longer than the field is not used rather than cut. With no usable summary the card says so and the field holds the person's own text, labelled as not a summary (empty when it does not fit). The pasted text itself is not saved |
| Scope | The model's: what Enginious is asked to deliver, then labelled lines for what the client or agency supplies, exclusions, dependencies and what is not yet confirmed. A scope longer than the field is not used, and the card says so |
| Technologies requested | The model's: what Enginious is asked to provide, with the stated quantity (1 when none is stated: the form's minimum). Not client-supplied equipment; no invented model, standard or quantity |
| Source | The model's choice from the eight existing sources, except that "Agency call (outbound)" is dropped unless the text shows Enginious made the contact. With no fitting source the field is empty and the card asks |

Nothing is saved until the person confirms the card; a repeated confirmation returns the original result. If the model's answer cannot be used, the card is built from what was read locally and asks only for what is missing.

**A request to be told protected information** ("What is Sara's salary?", "What discount did we give on the last quotation?") is answered by `jarvis.protected.guide`: JARVIS does not retrieve it. It checks the person's own access inside Enginious OS and then

| The person | Is told |
|---|---|
| Has access (Payroll: HR admin, Finance, CEO, CTO. Project budgets: a budget grant for the company. Saved prices: a Sales grant for the company. Own leave, claims and profile: everyone) | That JARVIS cannot show or discuss it, and which screen to open (a link) |
| Has no access | That they do not have access. **The words are the same whether or not the record or the person exists** |
| Access could not be checked | That it could not be checked, and no screen is suggested |

Asking for a draft that mentions a price the person supplies ("draft a reply offering 85 per item") is ordinary writing, not such a request.

## 5. Switches (existing controls first)

| Switch | Where | Effect |
|---|---|---|
| Main | `JARVIS_DISABLED=1`, or `jarvis_settings.enabled = false`, or the pilot list | Everything off |
| Writes | `jarvis_settings.writes_enabled = false` (existing), or `writes` in `JARVIS_PAUSE` | No review card that saves; everything else works |

## 6. Decisions and gaps for the owner

1. **Working costs and margins a person supplies** are treated as kind A (owner decision, 2026-11-11): they go out with the text. In a brief, an internal figure still never becomes the client budget on the card. Company results (turnover, profit, valuation) with a figure, financial documents and a pasted estimate document remain kind C.
2. **Contact details** (email addresses, phone numbers) in a brief are replaced before sending. They are not on the restricted list; this is data minimisation and can be dropped if the owner prefers the brief untouched.
3. **Reply and update no longer receive the enquiry record.** A drafted reply is written from the pasted text only, so it does not know the enquiry's recorded dates or venue unless the person includes them; the update action must be told the new value in full.
4. **The screen is a pattern list.** It cannot recognise every way of writing a sensitive or financial fact in free prose (a price written in words, an unusual currency, a figure split across sentences), and it can withhold a harmless sentence ("estimated 300 visitors" in a stored scope is removed because a financial word sits next to a number). That is why structured fields come first, stored free text is used only for one enquiry at a time, and the screen fails closed. Stored free text that cannot be separated is omitted and the card says so.
7. **Company-wide counts for any Sales user.** A summary counts every enquiry of the selected company, because the Enquiries and Reports screens already show those records to anyone with a Sales grant for it (`crm_has_access`, `20261115000000_crm_access_audit_settings.sql`). JARVIS adds no wider view. If the owner later narrows those screens, narrow this rule with them.
8. **Owner names are not shown or sent**: an enquiry is "owned by you" or "another owner".
5. **What Anthropic retains** is governed by the owner's agreement with Anthropic: `Unverified` here.
6. **Reviewing suggestions** is an owner-run query (`supabase/manual-sql/jarvis_memory_30_suggestions_review_readonly.sql`); there is no review screen yet.

## 7. Not built

Each needs its own rule in this document before any code:

1. Live lookups or summaries for Projects & Tasks, Inventory, Finance, People & HR or Approvals. A won enquiry is not a delivered project, and there is no approved Projects source.
2. Any financial summary, value-based metric or priced estimate through JARVIS. Pricing stays in the Estimate screen.
3. Sending email or messages, scheduling, autonomous follow-ups or outreach.
4. More creation actions (projects), and the Sales actions listed as "not conversational" in section 2.
