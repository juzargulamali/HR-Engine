## 1. What it is

One row is a **deliverable in a zone** (for example Entrance: Interactive LED welcome wall) with specifications, **one accountable owner**, a needed-by date and an optional reference image (an image already in Files & client plan; nothing is fetched from the internet). Under it are **breakdown lines** in the sections that apply: Hardware, Content / UI / UX, Programming, Installation, Testing. A simple supply-and-install job has a few rows and only the lines it needs.

**Entered once.** Release turns each work line into ONE task (`proj_create_task`, the existing task rules and notices) and each hardware line into ONE line on the project's **draft** equipment request (`inv_add_request_line`). The plan line stores the link, so saving, importing or releasing again never creates a second one. Submitting the request to the warehouse stays the existing button on the Equipment tab. **Progress is never stored in the plan**: it is read from the linked task and equipment line each time (`proj_dp_plan`, `lineProgress` in `model.ts`).

**Stable identifiers.** Every deliverable has a key (`D001`, ...) and every line a key (`L0001`, ...), unique per project and never reused. A deliverable is also unique by zone + name and a line by deliverable + section + description (case and surrounding spaces ignored), so a workbook row without a key finds the same record.

**Where a correction goes** (`proj_dp_raise_correction`): on a line, the section's delegate, else the deliverable's accountable owner; on a deliverable, its accountable owner; on a task, the head of the task's department team; on the agreed scope, the Project Manager. ## 4. Released work never changes silently

A change to a released deliverable (zone, name, specifications, owner, needed-by) or line (description, quantity, stock item, assignee, needed-by), from the screen or from Excel, is stored as a row in `proj_dp_changes` with only the fields that differ (`from` and `to`), who proposed it, an optional reason and whether it came from Excel. One open proposal per record: a newer one replaces (withdraws) the older. Approving applies it; rejecting needs a reason. The linked task is never rewritten: its assignee gets a notice and adjusts the task. A hardware line whose request is still a Draft takes an approved quantity (`inv_update_request_line`); once the request is with the warehouse the function refuses the change outright, so **an import or an edit cannot alter a booking or a reservation**.

## 5. Excel: Download template, Import Excel, Export Excel

Conventions follow the Clients & Agencies and Events imports (`lib/crm/clients-agencies/import/xlsx.ts`): .xlsx only, no macros, 4 MB, formulas are never run (cell values are read as data), cells are neutralised against spreadsheet formula injection on export, preview first and nothing saved until Confirm.

**Workbook.** Sheet **Deliverables**: Deliverable ID, Zone, Deliverable, Specifications, Accountable owner, Needed by, Reference image (export only), and on export the read-only columns Released and Progress. Sheet **Breakdown** (optional): Line ID, Deliverable ID (or Zone + Deliverable for a row that is new in the same workbook), Section, Description, Quantity, Stock item (Hardware), Assigned to (work sections), Needed by, Notes, and on export the read-only columns Released and Progress. Sheet **Instructions**. A simple job fills only Deliverables.

**Never read from a workbook:** progress, approvals, stock states, reservations, handover completion, the Released and Progress columns, the Reference image column. They stay in their own workflows.

**Import flow** (`/projects/[id]/delivery/import`):
1. Upload. The file is parsed and compared with the current plan. **Nothing changes.**
2. Preview: rows grouped as **Add**, **Update**, **Unchanged** and **Needs attention**, each error shown against its sheet, row and field. A person or stock item name that matches nobody, or more than one, needs an explicit choice (or "leave as it is"). Rows on released work are marked as proposals for the Project Manager. A changed quantity or stock item on equipment that is with the warehouse is Needs attention and is never sent. A stock item name equal to the one already recorded on the line is not looked up at all, so an untouched export stays Unchanged for a delegate who cannot read the stock list and for a retired item (fixed after the independent review, 2026-11-12).
3. Confirm ("Import N changes", off while anything needs attention). One transaction (`proj_dp_apply_import`): every row goes through the same functions as the screen. **Blank cells and missing rows never delete or clear anything.** If the plan changed after the preview was prepared (the plan revision differs) nothing is imported and the person is asked to upload again. If any row is refused, nothing of the file is saved.
4. Back to the Delivery plan. **Importing does not release anything**: tasks and equipment lines are still created only by Release.

Repeating the same import adds nothing (rows are matched by ID, else by zone + name, or deliverable + section + description).

## 8. Release 1: the Project Plan (migration `20270104000100_proj_project_plan_r1.sql`; draft PR)

Proven on a real PostgreSQL by `packages/rls-tests/test/proj-project-plan-r1.rls.test.ts`; the screens by `delivery-plan-view.test.tsx`, `insights.test.ts`, `model.test.ts` and, in a browser on a throwaway local database, `apps/web/os-shell-checks/project-plan-flow.mjs` (19 steps, fictional data; seed `seed/project-plan.sh`).

**Names and entry points.** The tab and page are **Project Plan** (`/projects/[id]/delivery`; the old address, `/delivery/import` and `/api/projects/[id]/delivery-plan/*` are unchanged). Entry: the tab; a **Project Plan** card at the top of **Work** (the Work overview stays); **Open the Project Plan** beside an accepted handover; **Accept handover** now opens the plan (`?from=handover` shows a welcome note with a link back to Work). A task released from the plan shows **From the Project Plan: D001 ...** in its panel.

**Shape.** Zone (optional) > technology / activation (row, with **Quantity**, accountable owner, ready-by) > requirements. Sections: **Hardware, Content, Apps, Engineering & integration, Site work**; plans made earlier keep `programming`, `installation`, `testing` (drawn as "(earlier plan)"). Delegation is by family: a delegate of Programming edits Apps; of Installation or Testing edits Site work. Only sections with lines are drawn; a delegated section with no lines on an activation is named as **Waiting for <person>: <section>**.

**Where each field is edited (all on the Project Plan, in the dialogs; nothing is typed twice).**

| Field | Where | Who |
|---|---|---|
| Technology / activation: name, zone, quantity, accountable owner, ready-by, specifications, reference image | **Add technology / activation**, **Edit** on the activation | Manager (released: becomes a proposal) |
| Hardware: item, quantity, specification (notes), needed-by, supply route (Inventory, Buy, Rent, Client supplied), stock item or none; for outside supply: owner, expected date, supplier | **Add requirement** / **Edit** (Hardware) | Manager; Hardware delegate |
| Content: deliverable, type, how many, format, resolution, orientation; owner, planned start, due, milestone, waits-for | same (Content) | Manager; Content delegate |
| Apps: app name, purpose, number of apps, platform, **number of devices** (one app on six screens = one app and six devices); owner, dates, milestone, waits-for | same (Apps) | Manager; Apps (or Programming) delegate |
| Engineering & integration: what, kind (controller, sensor, hardware programming, integration / test, other); owner, dates | same | Manager; Engineering delegate |

| Milestones and confirming a milestone | Existing milestone list on Work (`?ms=1`); the plan only links a requirement to one | Existing rules |

**Brings in the accepted scope once. This is a manual step: accepting a handover adds nothing to the plan by itself.** After **Accept handover** the plan opens with a welcome note and, above the summary strip, a highlighted **Next step: bring in the accepted technologies** panel (shown to the manager for as long as any accepted technology is not in the plan). `proj_dp_seed_scope` (button **Bring in accepted technologies (N)**, manager only) adds one row per technology of the accepted handover (name and quantity, no zone), keyed `tech:<name>`. A name already in the plan, or brought in and later removed, is skipped, so reopening the plan or retrying never duplicates a row or overwrites an edit. A scope that exists only as a brief (no structured technologies) is shown beside the plan; otherwise it is in a collapsed **Accepted scope (brief)**.

**What release creates (`proj_dp_release`, manager only, safe to repeat or run at the same time).** One task per work requirement through `proj_create_task` (assignee: the line's, else the activation's owner; due: the line's, else the activation's; **planned start**; **milestone**; description `Project Plan D001 / L0003 (Section)`). One line on the project's **draft** equipment request per **stock-matched** Inventory hardware line. Hardware without a stock match waits (reason "Choose the stock item for this hardware line first"); Buy, Rent and Client supplied hardware creates nothing for Warehouse. Dependencies between released requirements become `proj_task_dependencies` once both tasks exist (existing loop rule; a refusal is reported as skipped, never aborts the release). **Every release reconciles every released line of the project, whichever activations are selected**, so a prerequisite released after its dependent task (in another activation) is connected by the release that creates its task. **Dependencies added directly to a task are never removed**: the plan only adds its own, and when a plan line later stops naming a prerequisite only that prerequisite is taken off the task. A start date after the due date, a missing owner, a removed milestone or a person who left the project skips that line with a reason.

**What Warehouse sees.** Only what the Project Manager submits from the Equipment tab: the draft request with one line per released stock-matched line. Nothing is submitted by the plan. Reserved, Sent and Returned are shown on a line only from Inventory records; a linked record that cannot be read says so.

**Hardware states (computed from the line, never stored).** Matched to stock: ready to release; **Specification pending** (no specification and no match); **Needs stock match**; **Needs sourcing (Buy/Rent): no owner / no expected date**; Client supplied (expected date or "not recorded"); once released the equipment progress text. A manual line stays editable after release of everything else; match it (**Edit**, choose the stock item) and the next release adds it once.

**After release.** Description, quantity, stock item, owner, due, **planned start** and **milestone** of a released line, and the activation's fields, still become a proposal. **On approval** an owner, due, start or milestone change is applied to the linked task (**including a cleared start date, due date or milestone**: the task takes the *effective* plan value, which is empty, or for a due date the activation's own date when the line's own is cleared; an owner cannot be cleared, a task always has one) through `proj_reassign_task` / `proj_update_task` (their roles and rules decide; the task is the source after release and an assignee's own edits are never overwritten). If the task cannot take it (done or cancelled, or the approver has no task role), the line shows **Task update pending** (the reason, what the plan says, with "cleared" named for a cleared value, and what the task still has) with **Resolve** for the manager: **Retry the update** or **Keep the task as it is** (the plan then follows the task) (`proj_dp_reconcile_task`). Notes, details and dependencies of a released line change directly (dependencies through the existing dependency rules). How a released hardware line is supplied, and booked equipment, are changed on the Equipment tab.

**Summary strip (top).** From the plan records only: **Next site date** (the project's recorded install start, event start and end; "none recorded" and "dates have passed" are different statements); **Needs attention** counts, most urgent first: open blockers, missing owners, late dependencies (a predecessor not finished that ends after this starts), overdue tasks, hardware to source, equipment drafts to send, task updates pending, anything that could not be read; and the **Next action**, a link to the row (`?open=D001#dp-L0007`). A line whose task or equipment could not be read is a finding, never a clear row.

**Breakdown and Timeline.** `?view=timeline`. Breakdown: activations to expand (name, quantity, owner, ready-by, a readiness sentence), requirements with owner, planned start, due, status, blocker and next action, supply route, milestone, links **Open task**, **Review and send to Warehouse** / **Open equipment request**. Timeline: activations and requirements on the left, dates across (weekly ticks, a red line for today), from the same records (a released line takes its dates and status from its task); work with no start or due date of its own is listed under **Unscheduled**; a late predecessor is shown against the dependent. Read-only: dates change in Breakdown or on the task.

**Milestones.** Each milestone lists the tasks linked to it and the requirements planned for it but not yet released: **"N of M complete"** and the outstanding ones. **Readiness** (all linked tasks complete: "ready to confirm") is shown apart from **confirmation** (the milestone's own existing status); confirming stays on Work. "At risk" says when an outstanding date is after the milestone's.

**My Work, task detail, Project Plan and Timeline agree** because a released requirement's status, owner and dates are read from its task (`proj_dp_plan` joins `proj_tasks`). The existing Timeline tab (site and client plans) is unchanged and is a different page.

**Permissions.** Unchanged in kind: read = `proj_can_view_details`; deliverable edits and release = `proj_can_manage`; a section's lines = `proj_dp_can_edit_section` (now family-aware); delegation, seeding, reconcile = manager. The tables remain SELECT-only for signed-in users; every write is a function; the new helpers (`proj_dp_sync_task`, `proj_dp_clean_detail`, `proj_dp_line_loops`, `proj_dp_section_family`, `proj_dp_section_label`) are not callable by signed-in users. Another company's project is not readable or callable (tested). A finished project is read-only.

**Excel.** Unchanged columns; the template and imports now offer the five current sections and still read the earlier ones. Start dates, supply routes, details, milestones, waits-for and quantity of an activation are not in the workbook.

**Coverage rows added by Release 1** (screens and dialogs): Project Plan page (Breakdown / Timeline), Summary strip, Milestones panel, Accepted scope (brief), Bring in accepted technologies, Add requirement / Edit requirement (section-specific fields), Start from a sequence, Task update pending / Resolve, Project Plan card on Work, Open the Project Plan on Handovers.
