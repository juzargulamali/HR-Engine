Part of the Projects & Tasks Map: [coverage index](./projects-coverage-index.md) (every screen, numbered) and [action catalogue](./projects-action-catalogue.md) (every action that changes data). The two tables at the end of this file are their source.

Status: Projects & Tasks Phase 1 branch `claude/admiring-cray-uky379`, merged as PR #82 (merge `30c7895adc75f834a60b00ed3bca7015b1654282`, 2026-11-11); code read only, nothing run. No app, test, database or hosted project was started or queried for this file, so nothing here is a hosted fact. Every claim cites the file (and function) it was read from; `Unverified` marks what code reading could not confirm. Conventions as in `../README.md`. The compact index for the whole module is [`projects-phase1-changes.md`](./projects-phase1-changes.md); this file is the per-control reference for the shell, the directory and the personal screens only. Task detail, the project Work page, Handovers, Timeline, Equipment, Budget, People, Files, Changes, History and Completion are outside this file.

Words used below (all enforced in the database; the screens only hide what would be refused):

* **Projects access** = an active row in `proj_company_grants` for a company (`apps/web/src/lib/projects/context.ts`, `getProjectsContext`).
* **Sales-linked** = an active row in `proj_sales_links` for the person, while their Sales access for that company is active (`proj_sales_linked`, `supabase/migrations/20261120000100_proj_core_tables.sql`).
* **Member** = actively enrolled in the project and still eligible (`proj_is_active_member`, same file). **Phase 2B (merged as PR #86, merge `5b75ade`; migration `20270102000100` not applied by Claude):** once that migration is applied, an **Operations Manager** of the project's company (Projects capability `operations`) also reads the project's details without being enrolled, and manages nothing (they can comment on a task, raise a correction and post in the project's conversation, under their own name; they cannot add a file or a link (that needs a place on the project or founder: triggers `trg_proj_files_contributor`, `trg_proj_upload_intents_contributor`), create, assign, move or review tasks, edit the Delivery Plan, decide corrections or changes, manage or complete the project, or see restricted files or the commercial record; `proj_can_view_details`, `canViewProjectDetails`; [`operations.md`](./operations.md) section 2). In the directory such a person opens every project of that company in full, finished ones included (`proj_can_view_summary` also returns true for them).
* **Founder** = holds `founder` for the project's company (`proj_is_founder`, `20261120000000_proj_access_audit.sql`).
* **Manager** = founder, the Project Manager, or a person holding unexpired temporary project leadership (`proj_can_manage` and `proj_is_pm`, `20261120000100_proj_core_tables.sql`; app mirror `canManageProject`, `packages/domain/src/permissions/proj.ts`).
* **Assigner** = holds `assign_pm` (a founder holds every right: `proj_has_capability`).
* **Details level / summary level** = what `loadProjectView` returns (`apps/web/src/lib/projects/data.ts`, `projectViewLevel` in `packages/domain/src/permissions/proj.ts`): details for founders and members; summary for a Projects access holder who is not a member (ongoing projects only) and for a Sales-linked person; otherwise the project does not exist for that person.

All paths below are relative to the repository root; `app/...`, `components/...` and `lib/...` are short for `apps/web/src/app/(app)/...`, `apps/web/src/components/...` and `apps/web/src/lib/...`. Migrations are in `supabase/migrations/`.

## 3. Projects directory (`/projects`)

**Reach it:** menu Projects & Tasks > Projects; "Open Projects" on My Work; "View projects" and "Active projects" on My Day; the "All projects" back link on any project. **File:** `app/projects/page.tsx`.

**Who can see it:** anyone the shell lets in (section 1). The rows come from the function `proj_directory()` (`20261120000200_proj_projects_handover_functions.sql`), which returns only projects passing `proj_can_view_summary`: founders of the company, members, Projects access holders for projects that are not completed or archived, and Sales-linked people. It returns summary fields only (reference, name, kind, status, priority, ongoing flag, Project Manager and name, start and end dates, "is member", "is Sales linked"). Its own order is finished projects last, then end date, then reference; the page re-sorts (below).

**Purpose:** find a project, see what needs the person across Projects, move a project's status from the board, and add an internal project.

**Page state lives in the address** (`components/workspace/url-state.ts`): `q`, `company`, `kind`, `status`, `show`, `view`, `sort`, `open`. Unknown values fall back to defaults. `RememberList section="projects"` stores the address so "All projects" on a project returns to the same list (`components/workspace/list-memory.tsx`, session storage of this browser tab).

## 10. Project lifecycle rules behind these screens

Statuses (`PROJECT_STATUSES`, `packages/domain/src/projectLifecycle.ts`): Planning, In progress, Ready for installation, On site, On hold, Completed, Archived. Internal projects use Planning and In progress only. All status changes on these screens go through `proj_set_status`, except completing (`proj_complete_project`, outside this file) and reopening (`proj_reopen_project`).

| Move | Offered as | Rule in `proj_set_status` | Refusal (exact message) |
|---|---|---|---|
| One stage forward | "Move to <status>", note optional | Free | |
| Back, or skipping a stage | "Move to <status>", "Reason" required | A reason is required when the target is not exactly one stage ahead | "Moving a project backwards or skipping a state needs a reason" |
| To Ready for installation or On site on an internal project | Not offered | Refused | "Internal projects do not use installation and show states" |
| Put on hold | "Put on hold", "Why is it on hold?" and "Review date" | Stores `hold_reason`, `hold_review_date`, `status_before_hold` in `proj_project_details` | "Putting a project on hold needs a reason and a review date" |
| Resume | "Resume" (the only move of a held project) | Returns the project to `status_before_hold` and clears the hold fields | Any other target while on hold: "Resume the project before moving it to another state" |
| Complete | Not in this dialog | Refused here | "Use Complete project: it records the completion evidence" |
| Archive | "Archive" (the only move of a completed project) | Completed only; sets `archived_at` | "Only a completed project can be archived" |
| Anything else on a completed or archived project | Not offered | Refused | "A completed project can only be archived or reopened" |
| Same status as now | | Does nothing and reports success | |

Each accepted move raises `proj_projects.version` by one and writes one `status` line to `proj_change_log` with the reason or note (`proj_log_change`). No notice is sent for a status change made through `proj_set_status` (the function has no `proj_notify` call).

Changing the Project Manager is part of the lifecycle but its button is on the People page (Manage project > People & access > "Change Project Manager", `app/projects/[id]/people/people-forms.tsx`, `ReassignPmButton`), which is outside this file; its action is listed under Actions because it lives in `lib/actions/projectsCore.ts`.
