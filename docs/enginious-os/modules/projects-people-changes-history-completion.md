### 0.4 How every form here behaves

Every form in this file is an `ActionForm` (`apps/web/src/components/sales/action-form.tsx`), in a `Modal` where a dialog is named, except the completion form (section 5), which is its own form. Shared behaviour:

* The submit button is disabled while saving. A refused save keeps what the person typed. A successful save closes the dialog (`onDone`) or clears the form (`resetOnSuccess`), and the Projects pages are revalidated (`refreshProjects`, `apps/web/src/lib/projects/action-utils.ts`).
* Every dialog has a **Cancel** button that closes it without saving.
* A database refusal is shown in a red alert inside the form. The text is the database's own sentence unless `friendlyProjectError` (`apps/web/src/lib/projects/errors.ts`) rewrites it:

| Database answer contains | Shown instead |
|---|---|
| a timeout | "The save did not finish in time. Reload the page to see whether it went through, then try again if it did not." |
| "permission denied" or "row-level security" | "You are not allowed to do that." |
| a check, foreign key or input syntax violation | "One of the values is not allowed. Check the form and try again." |
| "duplicate key" | "That already exists." |
| missing table or function | "Projects & Tasks is not installed in this environment yet." |

* Every database function named here starts with `proj_lock_project` (`M200`), which answers "Project not found" when the project does not exist or the caller cannot see even its summary, so the two cases cannot be told apart.

Phone and desktop: no control in this file exists on one and not the other. Tables on People use the stacking table (`<Table stack>`), form grids collapse to one column below the `sm` width, and dialogs are the same `Modal`. How the dialogs and the stacked tables look on a real phone is `Unverified` (nothing was run).

## 1. People & access

* **Reach:** Manage project > **People & access**. URL `/projects/[id]/people`. Page title "Project people" (`P/[id]/people/page.tsx`).
* **Who can see it:** details level only (founder of the company, or member). Enforced by the page redirect (0.3) and by row-level security: `proj_project_members`, `proj_teams` and `proj_tasks` select policies use `proj_can_view_details(project_id)` (`M100`); the member list comes from `proj_project_people`, which returns nothing to anyone else (`M300`); `proj_sales_links` is readable with `proj_can_view_details` or by the linked person for their own row (`M100`).
* **Purpose:** who is on the project, in which department team, who leads, and which Sales people are linked. Changes are made by a Manager while the project is not finished (`canEdit = manager && live`).
* **What removal ends.** `proj_remove_member` (`M200`) sets `removed_at`, `removed_by` and `removal_reason` on the enrolment row, deletes the person's task collaborator rows for the project, hands their open tasks to the chosen member, writes a change log line, and deletes the person's `project_*` notifications for this project. From that moment `proj_is_active_member` is false for them, so every select policy above stops returning rows: the project's details, tasks, files, timeline, history and the old Discussion. The project's Chat group goes with it: membership of a project group is computed on every call from active enrolment (`chat_is_project_member`, `chat_is_member`, `M-chat`; [`app-chat.md`](./app-chat.md) section 9), so on the removed person's next Chat call the group, its preview, unread count, history and the right to post or be mentioned are gone. Nothing is stored that needs a second step. If the person still holds a Projects grant in the company and the project is live, they keep the summary row in the directory (`proj_can_view_summary`, `M100`). Tests: `rls` "removes access to details, discussion, files, notifications and calendars the moment a member is removed"; `packages/rls-tests/test/chat-project-groups.rls.test.ts`.
* **Revoking access without removal.** A member whose Projects grant is revoked (or, for a Sales participant, whose Sales access ends) stops being an active member at once without the enrolment row changing (`proj_is_active_member` comment, `M100`).

### 1.6 Gaps on this screen

* The three secondary reads on the page (open task counts, Sales links, and the member list's own data beyond `loadProjectView`) do not check for a read error, except the staff names. A failed read of the open tasks would show "0" in Open tasks and hide the "Who takes over" field (the database would still refuse the removal); a failed read of the Sales links would show "No Sales people are linked". This differs from the rule that a failed read must say it could not load (`CLAUDE.md`). Read in `P/[id]/people/page.tsx` (`tasksR.data ?? []`, `linksR.data ?? []`).

* On a finished project `proj_set_member_team`, `proj_remove_member`, `proj_remove_team` and `proj_end_acting_pm` contain no finished-project check of their own; the page hides those controls. Whether another database guard refuses them was not looked for: `Unverified`.

## 2. Feedback & changes

* **Reach:** Manage project > **Feedback & changes**. URL `/projects/[id]/changes`. Page title "Feedback & changes" (`P/[id]/changes/page.tsx`). Notifications about scope proposals and decisions link here (`apps/web/src/lib/projects/notification-text.ts`).
* **Who can see it:** details level only. Enforced by the page redirect and by the select policies `proj_can_view_details(project_id)` on `proj_feedback` and `proj_scope_changes` (`M500`). The cost effect table `proj_scope_change_commercial` is readable only with `view_commercial` (`M500`), and the page reads it only for a commercial reader.
* **Purpose:** record what the client asked for, give it a person and an outcome, and move anything outside the agreed scope through a recorded proposal and decision.
* **First line on the page:** "Nothing here approves scope, price or a deadline by itself: not a chat message, not an attachment, not feedback being recorded. A scope change is approved only by someone with scope approval, with a reason, on this page."
* On a finished project every button on this page is hidden; the lists stay readable.

## 6. Reopen project (dialog)

* **Reach:** Manage project > **Reopen project**, the last item, on a finished project (completed or archived). Not on History and not on the completion page. `manageItems` (`apps/web/src/lib/projects/workspace-nav.ts`), `ReopenDialog` (`P/[id]/overview-controls.tsx`).

## 7. Findings and verification gaps

Nothing in this file was run. In addition:

1. **Reopen is not on History.** The task brief and the notice on the completion page ("Its completion record is on the History tab. A founder can reopen it there if it was closed too early.") place it there; the code places it in the Manage project menu only. The notice also says "A founder", while a holder of the reopen right who is not a founder can reopen as well.
2. **Failed secondary reads are shown as empty** on People (open tasks, Sales links), Feedback & changes (all lists) and History (handover, completions, change log). Only the project itself, the staff names on People, the stand-alone decision page and the completion page distinguish a failed read. This is against the standing rule in `CLAUDE.md` ("A failed read must say it could not load").
3. **Completion review for a non-manager returns an empty list, not a refusal** (`proj_completion_review`). The page guards with `view.canManage` first, so it normally does not matter; where the page and the database disagree (for example temporary leadership that ends on a date the page and the database read differently), the page would show "Nothing is unfinished" and the completion itself would then be refused. The date the page uses for leadership comes from `todayUtc()` (`apps/web/src/lib/projects/data.ts`) and the database uses `current_date`; whether these can differ on the hosted database is `Unverified`.
4. The "Needs the client's confirmation" hint appears on **Complete project** for internal projects too.
5. Removal reason is optional in the form and in the database ("Reason (optional)").
6. `Unverified` items: where "Projects > Access" is; the notification wording for a person made responsible for feedback; what the stand-alone decision page shows right after a decision; phone layout of dialogs and stacked tables; whether typed completion decisions survive a visit to Documents in the same tab; whether any database guard beyond the functions read here blocks department, removal, team removal, ending leadership, withdrawal or cost edits on a finished project; where an audit reader reads the audit trail.
