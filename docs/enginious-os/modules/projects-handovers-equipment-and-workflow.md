## 1. Handovers (`/projects/handovers`)

**How to reach it.** Sidebar, Projects, Manage: **Handovers**. The entry is listed only for a person who holds `assign_pm` in any company, or who has a handover waiting on them (a `submitted` one they can assign, or a `pm_assigned` one that names them) (`web/components/nav/nav-groups.ts`, `loadProjectsNavAccess` in `web/lib/projects/context.ts`). Other ways in: the line "N handover(s) waiting on you" on Projects (`page/page.tsx`); the notice with **Open handovers** on My Work (`page/work/page.tsx`); My Day lines "Project handover waiting for you to accept" and "Project handover waiting for a project manager to be assigned" (`web/lib/my-day/attention.ts`), which link to one brief with `handoverHref` = `/projects/handovers?handover=<id>#handover-<id>` (`web/lib/projects/handover-list.ts`); and the in-app notices of section 1.3, which link to `/projects/handovers` (`web/lib/projects/notification-text.ts`). The address is always reachable by typing it; what it shows is decided by the reads below.

**Who can see it, and where that is enforced.**

* The Projects shell (`page/layout.tsx`) shows "Projects & Tasks is not installed in this environment yet. The database changes it needs have not been applied here, so nothing is shown." when the tables are missing, a load error when the person's access could not be read, and "You do not have Projects access. It is granted per company by the founders." to a person with no Projects grant and no Sales link to a project.
* Each handover row is returned only if the select policy `proj_handovers_select` (core tables) allows it: a Projects founder of the company; a holder of `assign_pm`; the person who prepared it or the Sales owner, if they still have Sales access to that company; the named Project Manager while the status is `pm_assigned`, `clarification_requested` or `accepted`; or anyone who can view the details of the project it created.
* The three actions are refused by their own functions, whatever the screen offers (section 1.2).

**Purpose.** Sales hands a won enquiry to delivery in one process of five steps: Prepare brief, Submit, Assign PM, PM accepts, Project created (`web/lib/projects/handover-process.ts`). This page is the Projects side: an Assigner names the Project Manager; the named Project Manager accepts (which creates the project) or asks Sales a question. The brief carries no prices, budgets or purchase-order details (page description; `web/components/projects/handover-brief.tsx`).

**What the page reads** (`page/handovers/page.tsx`): (1) every open handover (`submitted`, `pm_assigned`, `clarification_requested`), oldest submitted first, up to 500; (2) one page of 20 finished ones (`accepted`, `withdrawn`), newest first, chosen by `?page=`; (3) the one brief named by `?handover=<id>`, read by its id and never a `draft`. A staff directory (`proj_staff_directory`) is read only for a person who holds `assign_pm` or `manage_access`, to name Sales colleagues.

**Statuses and their labels** (`HANDOVER_STATUS_LABELS`, `packages/domain/src/projectLifecycle.ts`; column check in core tables): `draft` "Draft" (never listed here), `submitted` "Waiting for a Project Manager", `pm_assigned` "Waiting for the PM to accept", `clarification_requested` "Clarification requested", `accepted` "Accepted: project created", `withdrawn` "Withdrawn".

### 1.2 What the three functions do

All three are `SECURITY DEFINER` functions in the handover functions migration, called through the signed-in person's session by the server actions in `web/lib/actions/projectsCore.ts`. Errors pass through `friendlyProjectError` (`web/lib/projects/errors.ts`), which leaves these sentences as written and replaces only timeouts ("The save did not finish in time. Reload the page to see whether it went through, then try again if it did not."), permission errors, constraint errors and missing tables.

| Function | Who | Starting status | What it writes | Notification |
|---|---|---|---|---|
| `proj_assign_handover_pm(handover, person)` | Must be able to see the handover (`proj_lock_handover`: founder, `assign_pm` holder, the preparer or Sales owner with Sales access, or the named Project Manager; otherwise "Handover not found") and must hold `assign_pm` or `founder` | `submitted`, `pm_assigned` or `clarification_requested` | `proj_handovers`: `pm_user_id`, `pm_assigned_by`, `pm_assigned_at`, status `pm_assigned`, `version + 1`. The person must be eligible (`proj_user_eligible`: active profile and an active Projects grant in the company) | `project_handover_assigned` to the person named (never to the person acting; one unread notice per handover and person) |
| `proj_request_handover_clarification(handover, note)` | The named Project Manager only | `pm_assigned`. A repeat on `clarification_requested` returns without change | `proj_handovers`: status `clarification_requested`, `clarification_note`, `clarification_requested_at`, `clarification_requested_by`, `version + 1` | `project_handover_clarification` to the Sales owner, and to the preparer when that is a different person |
| `proj_accept_handover(handover)` returns the project id | The named Project Manager only. A founder who is not named can find the row but is refused with "Only the assigned Project Manager can accept the handover"; anyone else gets "Handover not found" | `pm_assigned` | See below | `project_handover_accepted` to the Sales owner and the preparer (once each) |

**Accepting, in order** (`proj_accept_handover`):

1. The handover row is locked, so two acceptances at the same moment run one after the other.
2. If the status is already `accepted`, the function returns the existing `project_id` to the named Project Manager and writes nothing. This is what a repeated click returns: the same project, and the action sends the browser to the same Work page.
3. Refusals: "This handover is not waiting for acceptance (status: <status>)"; "You no longer have Projects access in this company"; "The Sales opportunity is no longer Won, so the handover cannot be accepted. Ask Sales"; "A project already exists for this opportunity".
4. **One project per opportunity** is enforced three ways: the check in step 3, the unique index `uq_proj_projects_opportunity` on `proj_projects(crm_opportunity_id)`, and the unique index `uq_proj_handovers_open` (one handover that is not withdrawn per opportunity), both in core tables.
5. The new project gets:
   * `proj_projects`: a new reference (`proj_next_reference`), name = the handover title, `kind = client`, `status = planning`, the named Project Manager, start date = installation start (or the event start), end date = the event end, the opportunity id and the handover id.
   * `proj_project_details`: client name, location, site time zone, installation start, event start and end, scope, exclusions, technologies and risks, copied from the brief. The handover notes are not copied to the project details (they stay on the handover, which members of the project can read through the policy above).
   * `proj_project_members`: one row for the Project Manager with role `pm`.
   * `proj_sales_links`: the Sales owner (`handover_owner`) and, when different, the preparer (`handover_preparer`).
   * `proj_handovers`: status `accepted`, `accepted_by`, `accepted_at`, `project_id`, `version + 1`. From then on the trigger `proj_handovers_frozen` refuses any change ("An accepted handover is a historical record and cannot be changed").
   * **Equipment import.** The insert into `proj_projects` fires the trigger `inv_proj_projects_import` (function `inv_proj_after_insert`, planning functions), which calls `inv_import_handover_internal`. For a client project it creates one draft equipment request titled "Equipment from the Sales handover" (`source = sales_handover`), with whole-day dates taken from the brief, and expands every technology whose name matches a complete technology template of that company (compared without regard to case or surrounding spaces) into request lines. Technologies with no complete template are written into the request note and the import log, not invented as lines. Nothing is imported, and the reason is logged, when Inventory is not set up or is switched off for the company, or when the brief lists no technologies. A failure is written to `inv_import_log` and never blocks the acceptance. The import can be run again from the Equipment tab (section 2.2).
6. Nothing else is created: no tasks, no budget, no chat message. The project's chat group is created the first time a member's group list or the project's group is asked for (`app-chat.md` section 9).

### 2.5 Dispatch & return notes on the project

Panel **Dispatch & return notes** ("What the warehouse recorded as sent to this project and received back, kept exactly as recorded. The Project Manager acknowledges each one; nothing waits for the answer."), `web/components/inventory/notes/notes-section.tsx`, `note-card.tsx`, `note-actions.tsx`, `note-pdf-links.tsx`.

**Where notes come from, and the switch.** A note is made by `inv_make_project_note` inside the warehouse's dispatch (`inv_dispatch_to_project`) or return (`inv_return_from_project`) transaction, and only when `inv_project_notes_enabled(company)` is true, which reads `inv_company_settings.project_notes_enabled` for the company passed to the movement (notes migration). The column's default is `false`. With it false, the dispatch and return are recorded and no note is made, so this panel does not appear. The setter `inv_set_project_notes` is for an Inventory founder; `04` section 1.4 records that no app screen calls it. Whether it is on for any company is not stated here.

**Who reads and who answers.** Notes, their events and the derived state are readable by anyone who can view the project's details and by Inventory people who can view stock in the warehouse's company (policies `inv_project_notes_select`, `inv_project_note_events_select`; the state view runs with the reader's rights). A note or event can never be updated or deleted (guard trigger `inv_project_notes_frozen`, per the migration header).

**Sections inside the panel**: **Dispatch waiting for you (N)** / **Dispatch waiting for the Project Manager (N)**; **Returned, please confirm (N)** / **Returned, waiting for the Project Manager (N)**; **Difference reported, waiting for the warehouse (N)**; **Other notes (N)** or **Notes (N)**. The first wording of each pair is shown to a Manager, the second to other members. Footer: "A correction is a new note that cites the old one. The old note and its history are never changed."

### 2.7 Request statuses, what "still out" means, and completion

**Request statuses** (labels in `REQUEST_STATUS_WORDS`, `web/lib/inventory/words.ts`; transitions in `inv_submit_request`, `inv_refresh_request_status` in stock functions, `inv_cancel_request_internal`):

| Label | Database value | How a project request gets there |
|---|---|---|
| **Draft** | `draft` | Created by "New equipment request" or by the handover import. Nothing is reserved and the warehouse has not been asked |
| **Waiting for the warehouse** | `submitted` | "Submit to the warehouse". Submitting reserves nothing |
| **Being prepared** | `in_progress` | Something has been dispatched for the request, and at least one line that is not cancelled is not yet fully dispatched |
| **All dispatched** | `fulfilled` | Every line that is not cancelled has been dispatched in full |
| **Closed** | `closed` | Every such line is fully dispatched and everything dispatched has been recorded as returned |
| **Cancelled** | `cancelled` | "Cancel this request", or the project was completed or archived while the request was Draft or Waiting for the warehouse |

Reserving alone does not change the status (the status is recalculated from dispatched and returned quantities). `Unverified`: which stock functions call `inv_refresh_request_status` was not traced line by line; the rule above is the function's own text.

**"Still out"** means dispatched to the project and not yet recorded by the warehouse as returned. On this tab it is built from three lists (`outstandingView`, `web/lib/inventory/workspace.ts`; `inv_project_equipment`, latest definition in `mig/20261201000800_inv_project_equipment_unlinked.sql`):

1. Reservations of the project's requests where the dispatched quantity is larger than the returned quantity (named by request).
2. Units and quantities the project holds that are not part of any request ("not part of a request"): the warehouse can dispatch to a project without naming a request.
3. Counted stock that could have been returned for more than one request or line: shown once for the project with the badge **Project level**, never split per request by guesswork.

A unit recorded as missing stays in the list as "Recorded as missing ... not returned". "Overdue" means the expected return time has passed. Cancelling a line or a request releases only what was not dispatched; it does not bring equipment back.

**Completion does not return equipment.** `proj_complete_project` (`mig/20261120000500_proj_feedback_plans_files_completion.sql`) sets the project to `completed`. The trigger `inv_proj_projects_release` (function `inv_proj_after_status`, planning functions) then cancels the project's requests that are Draft or Waiting for the warehouse and releases the unused reservations of those Being prepared, with the reason "Project completed" (or "Project archived"). Dispatched equipment stays outstanding, and this tab says so: "The project is completed but equipment is still out. Completing a project does not return it." A failure in that trigger is logged to `inv_import_log` and never blocks the completion. Returns are recorded only by the warehouse (`inv_return_from_project`, reached from Inventory; `inv_get_project(p_project_id, false)` in that function is read as allowing a finished project, `Unverified`: the helper's body was not read).
