## 1. What it is

One assistant for the whole app, with **one floating launcher on the right edge** of every signed-in page (`apps/web/src/components/jarvis/jarvis-launcher.tsx`, drawn from `apps/web/src/app/(app)/layout.tsx`). It is **OFF by default** and appears only for people the server says may use it (section 5). It knows one capability, **Sales & CRM**, and seven actions (section 2): turn a pasted brief into a **review card** for a new enquiry, draft a client reply, answer how-to questions, register a client or agency, update an enquiry, change its status and turn meeting notes into an activity and follow-up. **Nothing is saved until the person presses the confirm button** on the action's card (a draft and a help answer save nothing and have no such button).

* Launcher: accessible name "Open JARVIS" (the words slide out on hover or keyboard focus; click, tap and Enter/Space all open it). Phone: a round button above the bottom bar. Original compact SVG mark (`jarvis-mark.tsx`): a geometric J that turns inward and ends in a small square; colour from the token `--jarvis-mark` (Enginious teal `#1D5D6C` in the light theme, cyan `#27CDD8` in the dark theme; `apps/web/src/app/os-design.css`); a brief pulse on opening, off for `prefers-reduced-motion`.
* Panel: title "JARVIS", subtitle "Enginious OS assistant", badge "Sales & CRM", first line "Paste a brief and I'll turn it into an enquiry for you to review." Desktop: a side panel (not modal, so the page stays usable while it is open). Phone: a full-height bottom sheet (modal, focus trapped). Escape closes it and focus returns to the launcher; opening moves focus to the message box.
* Context chips: the **active company** (a picker when the person may use JARVIS for more than one) and, on `/sales/opportunities/<id>` or the list's `?open=<id>`, the **enquiry** the page is about. This is a **hint, not permission**: the enquiry is re-read through the person's own session (`assistant.context`, `lib/jarvis/assistant.ts`); one the person cannot read is not revealed. If the route moves to an enquiry of another company the panel switches company **visibly** (a notice) and a review made for the other company can no longer be used; a review is bound to its company, so it is never retargeted silently.
* My Day is an entry point only: JARVIS does not copy its task list.
* **No persistent chat history.** The conversation lives in the panel component's memory; reloading the page clears it. The server stores only the action ledger and the daily usage counter (section 6). Test: `jarvis-launcher.test.tsx` ("stores nothing in the browser"), `create-from-brief.test.ts` (static scan: no storage, no file writes, no privileged client, no direct table writes).

A mode only chooses WHICH registered action the text goes to; the server resolves the id in its deny-by-default registry. Short typed sentences ("move this to Qualified", "how do I log a follow-up?") are routed by fixed rules (`routeMessage`). The actions that work on ONE existing enquiry use the enquiry the page shows (a hint), or one named by its reference (`OPP-UAE-2026-0001`) in the text; either is re-read through the person's own session, must belong to the selected company, and is bound into the confirmation.

### 2.1 What each part-2 action does, and what proves it

* **Draft a reply** (`sales/draft-reply.ts`, `sales/reply-guard.ts`). Input: an authorised enquiry plus the person's pasted conversation. Output: a subject and body in the card with a **Copy** button, and **above** it a "to confirm" list. There is **no `execute`**: the proposal is never valid, so no confirmation exists; nothing is sent, no inbox is read, nothing is written (tests assert the RPC log holds no write). The provider receives only the fixed instructions, today's date, the enquiry's **reply-relevant facts** (reference, title, agency and end-client names, event dates, installation, location, technologies, scope, brief summary, the client's budget note) and the person's text, in tagged blocks the text cannot close. **Never sent:** the internal value and currency, the owner, ids, any other enquiry (test: the payload is checked for each). The model's own "to confirm" list is not trusted: **code scans the draft** for prices, dates, availability wording and promises of a quotation, fixed price or reservation and adds everything not found in the enquiry facts or the person's text; a value the model claims came from the enquiry or the text is checked against those sources and moved to the list if absent. Tests: `draft-reply.test.ts` (19).
* **Help** (`sales/help-answer.ts`, `help/guidance.ts`). An app question is answered from a **reviewed, staff-facing guidance set** (19 short topics, each with real screen paths; a test checks every link against the app's page routes and that the text contains no code paths, SQL, migration names, table names or permission internals) chosen by a deterministic keyword match, with **no provider call, no allowance used and no record read** (test: the read log is empty). An app question with no guidance says so and lists the topics. Only a **general (non-app) question** reaches the model, with the question alone. Projects, Inventory and People & HR get "where to find it" guidance only. The refusal list also blocks requests for the system prompt, the tool list, the internal docs and other people's data before any provider call; a single-line how-to question that merely names another module is guidance (`classifier.ts` `howTo`). Tests: `help-answer.test.ts`, `help/guidance.test.ts`.
* **Register a client or agency** (`sales/organisation-register.ts`). Step 1 searches the organisations the person may see (same name, same website domain, similar name) and offers "register as new"; step 2 is a **separate card** with the exact type (agency, direct client, end client, technology company; at least one) and the fields (name, country, website, place, note), with its own confirmation. A same-name or same-website organisation must be ticked as "different" (acknowledged ids are checked again at execution and by the database wrapper, which uses `crm_import_candidates`). The write is `jarvis_register_organisation` around the existing `crm_create_organisation_profile` with this company's account profile and **no owner, lead source, exhibition or contacts**. The create-from-brief card offers "Register ... with JARVIS" for an organisation that is not recorded.
* **Update an enquiry** (`sales/enquiry-update.ts`, `enquiry-update-values.ts`). **Allowlist (in code and in SQL):** title, brief, event start, event end, installation, location, technologies, scope, waiting on, budget note. **Not reachable:** owner, stage, agency, end client, value, currency, payment terms, exclusions, risks, evidence, files, proposals, Zoho, handover, closure. The model returns only the allowlisted fields; everything else it returns is dropped; the card shows each change **before -> after**; the confirmation is bound to the **record version**, rechecked at execution ("changed by someone else": fresh review) and passed to `crm_update_opportunity`'s expected-version rule by `jarvis_update_enquiry`. A repeat of a saved confirmation returns the original result although the version moved on.
* **Change status** (`sales/enquiry-stage.ts`, `stage-transitions.ts`). No provider: the stage is read from the words by fixed rules or chosen on the card. Section 2.2.
* **Meeting notes** (`sales/meeting-record.ts`, `meeting-values.ts`). The provider receives only the notes and fixed instructions. Output: ONE activity (the real types: meeting, call, email, note, client response; text; optional date it happened; internal flag) and ONE follow-up (title, due date, time, type) **for the person**. **The date is never guessed:** the model's date is accepted only if the notes state it exactly or by an unambiguous day word (today, tomorrow, next Monday, in N days/weeks) (`acceptDate`); otherwise the card **asks** and cannot be saved. **Atomicity decision: ONE confirmation and ONE ledger-backed wrapper (`jarvis_record_meeting`) that calls the existing `crm_add_activity` and `crm_create_follow_up` in the same transaction**, so both are saved or neither (no "half-state" to report); a refusal (Won enquiry has no follow-ups; future date; Lost) rolls both back and is recorded once and replayed. The assignee is always the person (no assignee argument exists).

### 2.2 Status transitions (derived from `crm_move_stage`; JARVIS is deliberately narrower)

The database allows, among the six working stages, one step back or any step forward, and gates two TARGETS on evidence. JARVIS offers **exactly one step in either direction**, and a move INTO a gated stage only when its evidence is recorded (checked when the card is built and again at execution; the database checks it a third time).

| Move | JARVIS | Why |
|---|---|---|
| New enquiry -> Qualified; Qualified -> Proposal preparation; Quote sent -> Negotiation | **Enabled** | one step forward, no gate in `crm_move_stage` |
| Qualified -> New enquiry; Proposal preparation -> Qualified; Proposal sent -> Proposal preparation | **Enabled** | one step back, no gate on the target |
| Proposal preparation -> Proposal sent; Quote sent -> Proposal sent (back) | **Enabled only when** a proposal is recorded as `sent` or `accepted` (a draft or an estimate does not count; an estimate cannot be recorded as sent) | the existing gate on `proposal_sent` |
| Proposal sent -> Quote sent; Negotiation -> Quote sent (back) | **Enabled only when** the Zoho Books quote reference is recorded (blank does not count) | the existing gate on `quote_sent` |
| Any skip (for example New -> Proposal preparation, Proposal preparation -> Negotiation), two or more steps back | **Disabled** | JARVIS moves one step at a time; the enquiry page can skip forward |
| To or from On hold, Won, Lost; reopen; handover | **Disabled, always** | separate forms, evidence, approvals and side effects; the panel and this document say so; `jarvis_change_stage` refuses them in SQL before the ledger |

A failed read of the evidence keeps the gated moves off ("Could not check"), never assumed. `transitionTable()` generates all 30 pairs and `enquiry-stage.test.ts` asserts each; `jarvis-actions.rls.test.ts` walks every ungated move forward and back, both gated moves with and without their evidence, and the refusals, on a real database.

## 3. How "create an enquiry from a brief" works

1. **Paste** a WhatsApp message, email or rough brief (limit `JARVIS_MAX_INPUT_CHARS`, default 6000).
2. **Refusal list first** (`lib/jarvis/classifier.ts`): a request for payroll, salaries, leave, other modules' records, raw SQL, source code, credentials, configuration, deployment, permission changes, or deletion of records or audit history is refused **before** any provider call or usage count. It looks for a request (a verb aimed at the thing), not the word, so "a payroll company's gala" passes. It is defence in depth: the wall is that no such action exists and the database permissions apply whatever the text says.
3. **Extraction** (`provider/`): the provider receives **only** the pasted text, fixed instructions and the field schema (one forced tool, `record_fields`). The model returns a plain object; the server prunes it to the known keys, length-limits every string and blanks every invalid value (`sales/extraction.ts`). Anything else it returns (an "execute" flag, a company id, an organisation id, an owner, a role) is dropped. **Organisation names are search texts only; ids are never taken from the model.**
4. **Fields**: exactly the existing create-enquiry form's (`createOpportunitySchema`, `apps/web/src/lib/actions/crm.ts:63`; `sales-enquiries.md` section 3): title, source (the 8 fixed options), agency, end client, currency, value, budget note, brief, event start and end, installation, location, technologies (name and whole quantity), scope, waiting on, next action (title, due date, time 10:00 Dubai, type). Unknown optional fields stay **blank**. Owner is always the approving person (the form's default); contacts are linked on the enquiry page afterwards. The enquiry's Brief field holds a short **summary**, not the pasted text.
5. **Agency versus end client** (the Clients & Agencies role model, `sales-clients-and-agencies.md` section 9.2): an organisation is offered for a field only if it carries that role (`lib/crm/organisation-roles.ts`). One exact match with the right role is selected; a partial or ambiguous match is a **question** with options; an organisation that exists without the role says so; one that does not exist says "Register it in Clients & Agencies first". **JARVIS never creates an organisation** (`jarvis.sales.organisation.register` is disabled). The look-ups run through the person's own session (RLS) and return only id, name and place.
6. **Duplicates** (`sales/duplicates.ts`): the same deterministic rules as the form (`crm_find_duplicate_candidates` + `findLikelyDuplicates`, `packages/domain/src/crmDuplicates.ts`), limited to the **selected company**. A "likely" duplicate must be acknowledged on the card ("These are not the same enquiry") and is **re-checked at execution**; a check that fails fails closed.
7. **Clarifying questions** appear on the card (missing title, source, next action, date; ambiguous organisation); the person answers by filling the field or picking an option and presses "Review changes" (a revise call: no provider call, no usage). Required fields and rules are those of the form and the database (next-action date not before today in Dubai; show end not before start).
8. **Review card** (`review-card.tsx`): editable fields, the exact company, linked organisations, duplicates, what is still missing. **"Create enquiry" is enabled only when** the card is complete and valid, unchanged since its review, for the current company, and any likely duplicate was acknowledged.
9. **Create**: the explicit button calls the one write endpoint (`jarvisConfirm`, `apps/web/src/lib/actions/jarvis.ts`). The result shows the **real reference** (`OPP-<code>-<year>-<nnnn>`) and a link **only after** the app has read the enquiry back through the person's own session (`verify`). An unknown answer shows "Checking the original result" (a read-only status call by confirmation id) and **never offers a second create**.

## 5. Access: never broader than the person's own permissions

Checked **on every request** (propose, review, confirm, status, context), in this order (`createDispatcher.authorize`, `apps/web/src/lib/jarvis/dispatcher.ts:48`):

1. the environment: `JARVIS_DISABLED`, a configured provider (key, or the simulated one outside production), and in production `JARVIS_CONFIRMATION_SECRET`; any failure = "unavailable" and ordinary CRM is unaffected;
2. the **authenticated session** (`supabase.auth.getUser()`); no user id, company, flag or role is read from the browser;
3. the database controls through `jarvis_my_access(company)`: the **global switch** (`enabled`), the **pilot allowlist** (`jarvis_pilot_users`), the **write kill switch** (`writes_enabled`; without it read-only help keeps working but creating is refused) and the optional **company list** (`jarvis_pilot_companies`; empty = no company restriction);
4. the **module grant for the selected company** (an active Sales grant), then the action's own rule and the records' visibility (RLS) inside the action.

**Hiding the launcher is not access control**: the layout asks the same server (`lib/jarvis/launcher.ts`) only to decide whether to draw it; every call re-checks. A pilot person with no Sales grant gets no launcher and, if they call the server actions directly, a refusal. Access revoked between the review and the click is refused (`create-from-brief.test.ts`, `jarvis-flow.mjs`).

**Hard exclusions, regardless of the person's other roles:** JARVIS has no tool for salaries, leave, payroll, other modules' records, raw SQL, source code, credentials, application configuration, deployments, permission changes, or deletion of records or audit history. The registry is deny by default (`lib/jarvis/registry.ts`): an id that is not registered and enabled is refused as unknown; the classifier refuses such requests before the provider; if one reached the model the model has no tool for it and the server would not execute it.

## 6. Confirmation, retries and what is stored

* **Server-bound confirmation (two checks: the app and, decisively, the database).** `propose` never writes. When the card is valid it returns a **proof**: an HMAC-SHA256 (`JARVIS_CONFIRMATION_SECRET`; `lib/jarvis/token.ts`) over the authenticated user id, the company id, the action id, the target (`new`, or a record id), the record version (or a fixed marker), the expiry (`JARVIS_CONFIRMATION_TTL_MINUTES`, default 15), a unique proof id (the confirmation id) and the SHA-256 of the **exact payload text** the database wrapper will receive. `jarvisConfirm` takes only the token plus the reviewed values; the app verifies the proof (defence in depth), rebuilds the payload text from the values and **rejects** tampered, expired, wrong-user, wrong-company, wrong-action or edited confirmations BEFORE any database call, rechecks authorisation and the organisations, and asks for a fresh review when anything differs; **then every write wrapper verifies the same proof again inside the database (section 6.1) before anything is written**. **A chat message such as "confirmed" never executes anything**: it is just another brief; only the card's button calls the write endpoint. **Editing a value on the card needs a new review and a NEW proof** (the payload hash changes; an old proof cannot be reused with a modified payload: tested). The record **version** is part of the proof for **update** and **change status**: at execution the app re-reads it and, if anything changed it, the person must review again; the database checks that the signed version is still the record's current version (and `crm_update_opportunity` / `crm_move_stage` check the expected version a third time). A repeat of an already saved confirmation skips the version check on purpose (the database returns the ORIGINAL result), which is why a double click after a successful update says "already saved" instead of "changed". The meeting action binds no version (neither existing function has one; the proof carries the "no version" marker); the enquiry's own rules decide.
* **Idempotency.** The ledger `jarvis_action_ledger` has a **unique confirmation id**. `jarvis_create_enquiry` takes an advisory lock on it, inserts the ledger row and creates the enquiry in **one database transaction**; a repeat returns the **original** result and creates nothing; N concurrent calls create exactly one (RLS test: 12 in parallel). A used confirmation id with a different person, company or reviewed values is refused. A refusal by the existing rules (for example a missing agency role) is recorded once as `failed`, creates nothing, consumes no reference number, and is replayed on a repeat: a failed confirmation is final, the person reviews again.
* **Timeouts and restarts.** The ambiguous case (network error or timeout, or a save that could not be read back) shows "Checking the original result": the panel polls the read-only `jarvisStatus` by confirmation id (the person's own ledger row). A simulated server restart between propose and execute still works (the token is stateless and the ledger is durable): tested in `create-from-brief.test.ts`.
* **What is stored.** `jarvis_action_ledger`: confirmation id, user, company, action id, target (`new`), the SHA-256 of the signed payload text (not the text), status, the created enquiry's id and reference, an error code and message from the database's own refusal text, timestamps. **No brief, email body, prompt, model output or secret.** `jarvis_usage`: requests per person per Dubai day. Plus the usual CRM timeline: the new enquiry gets its ordinary "Enquiry created." event and a second event "Enquiry created through JARVIS ..." whose actor is the approving person (`helpers.ts` `describeEvent`).
* **Logs.** `lib/jarvis/log.ts` accepts only short identifier-like fields (event, action id, outcome code, provider kind, duration); text is dropped. Test: a full flow with a marker string and a payroll request logs none of the brief, names, token or ids.

### 6.1 The confirmation boundary: what is signed, where it is verified, what a direct caller can and cannot do

**The problem it closes.** A confirmation token that only the app server checks is no boundary: the database wrappers are callable through the platform API by any signed-in person, and an eligible pilot person (pilot on, Sales grant, right company) could call one directly with a confirmation id and hash they made up and write something nobody reviewed. **A caller-supplied id and hash are not proof.** There is no service-role key or privileged proxy anywhere in JARVIS, so the only way the database can trust that "the server approved this exact action" is a keyed MAC that the signed-in person can never forge.

**What is signed.** HMAC-SHA256, keyed with the proof key, over this exact text (fields joined by a line feed, format version 1; the same text is built in `lib/jarvis/token.ts` and in `jarvis_verify_proof`):

```
JARVIS-PROOF-V1
<proof id = the confirmation id, a lower-case uuid; unique per proposal, part of the MAC so it cannot be invented>
<the approving person = auth.uid() in SQL>
<company id>
<action id: each wrapper hard-codes its own>
<target: the record id, or the word new>
<record version as an integer, or a single hyphen when the action has no version>
<expiry, epoch seconds>
<SHA-256 (64 lower-case hex) of the exact payload TEXT, UTF-8>
```

The **payload** is the object the wrapper uses to do the write (`wirePayload` of each action, canonical JSON: keys sorted), sent to the wrapper as `p_payload` **text**; SQL recomputes its SHA-256 over those exact bytes and casts it to jsonb only after the MAC has checked. Each wrapper takes `p_confirmation, p_company, p_target, p_version, p_expires, p_mac, p_payload` (the person is never a parameter). Test vectors computed independently with Node `crypto` are in `supabase/tests/jarvis-proof-vectors.json`: the TypeScript signer (`platform-basics.test.ts`) and the SQL verifier (`jarvis-proof.rls.test.ts`) must both reproduce them.

**Where it is verified.** `jarvis_verify_proof` (`SECURITY DEFINER`, fixed `search_path`, not callable by signed-in users) is the first statement of every write wrapper, before any lock, ledger row or call of an existing function. It: takes the person from `auth.uid()`; fails closed with **JV004** when no key is set; recomputes the MAC and compares it byte by byte in constant-time style (**JV002** when it differs, with no hint why); then, only for a genuine proof, checks the expiry against the **database clock** (`now()`; **JV003**). The wrapper then checks the shape its own action needs (create/register: target `new`, no version; update/change status: a record target and a version; meeting: a record target, no version), that the payload's company equals the signed company (create/register) or that the record belongs to the signed company (others), that the signed version is still the record's current version (update/change status; **40001**, nothing written), and only then takes the advisory lock, writes the ledger row and calls the existing function. **A refused proof writes nothing at all**: no business record, no ledger row, no timeline event. (Refusals are not logged to the ledger on purpose: an unauthenticated-proof request must not be able to fill the audit table.)

**The key.** `jarvis_proof_key`: one row, RLS on, **no policy, no privilege for `public`, `anon`, `authenticated` or the platform's `service_role`**; read only by the database's own definer functions; set or rotated only by the owner with `jarvis_set_proof_key(text)` (not executable by any API role) to the same value as the app's `JARVIS_CONFIRMATION_SECRET`. It never appears in the repository, a log, the client bundle or any query result: `jarvis_my_access()` returns three booleans; the verify pack shows only "set / not set". **Not set = every wrapper fails closed** (and the migration creates the table empty, so nothing can write until the owner sets it). **Rotation:** set the database key and the environment variable to the new value together (`docs/jarvis-deployment.md`): proofs signed with the old key stop working at once and are simply re-issued when the person reviews again (they expire within the TTL anyway); until both match JARVIS fails closed with a plain message and ordinary CRM is unaffected. **Rollback removes the key table** (the secret itself stays in the app's environment; the owner sets it again after a re-apply).

**MAC implementation (decision).** HMAC-SHA256 written in plpgsql (`jarvis_hmac_sha256`, RFC 2104) on top of the **built-in `sha256(bytea)`** (PostgreSQL 11+), not `pgcrypto`: no extension is needed, the behaviour is identical on every Postgres and on Supabase (where `pgcrypto` lives in the `extensions` schema and would need that schema on every definer function's `search_path`), and the preflight only checks that `sha256` exists. It is proved equal to Node's `crypto.createHmac('sha256', ...)` on five vectors (short key, 64-byte key, 100-byte key hashed first, empty message, 1000-byte message, non-ASCII text).

**What a direct caller can and cannot do now.** An eligible pilot person calling a wrapper through the API directly: **cannot** write anything with an invented confirmation id or hash, an altered payload (one changed character is enough), an expired proof, a proof made for another person, company, action, target or version, or while the key is not set; **cannot** read or change the key, call the proof functions or the ledger helpers, write the ledger, or learn another person's confirmations. **Can**, within the existing CRM rules and the same identity, use a **genuine proof the server issued to them** (they receive their own token in the browser) with exactly the payload it was issued for, once: which is exactly the action the server validated for them and nothing else. A genuine proof proves "the server validated and approved this exact action for this person", not "this person clicked the button": the button is the app's job (a direct caller who first calls the propose endpoint with their own values obtains a proof for those values, which they could equally have saved through the ordinary form). One deliberate exception: **`p_ack` (organisation registration)** carries the ids of same-name organisations the person ticked as "different"; it is not signed because it can only relax the duplicate guard for the very organisation the proof already fixes; the app checks the guard first and the database checks it again.

**Wrapper and bookkeeping audit (every `jarvis_*` function a signed-in person can run).**

| Function | Granted to `authenticated` | Verifies the proof | Why |
|---|---|---|---|
| `jarvis_create_enquiry` | yes | **yes** (first statement) | business write |
| `jarvis_register_organisation` | yes | **yes** | business write |
| `jarvis_update_enquiry` | yes | **yes** (+ signed version = current) | business write |
| `jarvis_change_stage` | yes | **yes** (+ signed version = current) | business write |
| `jarvis_record_meeting` | yes | **yes** | business write (activity and follow-up atomically) |
| `jarvis_usage_take(limit)` | yes | no | bookkeeping only: it increments **the caller's own** daily counter (`auth.uid()`; there is no argument that names another person), creates no business record, writes no ledger row and cannot touch another person's row; a direct call can only use up the caller's own allowance. Refused for people who are not eligible. Tested. |
| `jarvis_my_access(company)` | yes | no | read only: three booleans about the caller; never touches the key |
| `jarvis_ledger_enter`, `_done`, `_fail`, `_json` | **no** | n/a | internal helpers called only by the wrappers (which verified the proof) |
| `jarvis_verify_proof`, `jarvis_hmac_sha256`, `jarvis_set_proof_key` | **no** (not for `public`, `anon`, `authenticated`, `service_role`) | n/a | the proof machinery; the setter is for the owner |
| tables | `jarvis_action_ledger`: select own rows only; all others (`jarvis_settings`, `jarvis_pilot_users`, `jarvis_pilot_companies`, `jarvis_usage`, `jarvis_proof_key`): no privilege | n/a | no direct writes anywhere |

The verify pack checks the same facts in the database: signed-in users can execute exactly seven `jarvis_*` functions (so no old signature that skips the proof is left behind), no `jarvis_*` function is callable by `anon` or `public`, each wrapper verifies the proof with its own action id before any lock or write, and the proof key is "set" or "not set" without ever showing it.

## 7. Data that leaves Enginious OS, and what the app keeps

* **To the AI provider** (Anthropic Messages API, `provider/anthropic.ts`, server side only): the **pasted text** the person sends, the fixed instructions, today's date and the field schema. **Nothing else**: no enquiries, no organisations, no ids, no company data, no other module, no tool list of other modules. Candidate organisations from look-ups stay in Enginious OS (they are shown to the person; they are not sent to the model). A test asserts the exact request keys and that no record, organisation or id appears in them (`create-from-brief.test.ts`, "denied data never reaches the provider").
* **Part 2, per action** (each asserted on the simulated provider's received payload in its test file): *draft a reply* gets the enquiry's reply-relevant facts and the pasted conversation (never the internal value, owner, ids or other enquiries); *update* gets the current values of the allowlisted fields of that one enquiry and the request; *meeting notes* gets only the notes; *help* gets nothing for an app question and only the question for a general one; *change status* and *register* use no provider at all. The guidance set, the internal map and the action catalogue are never sent.
* **Never**: the API key to the browser, Git, logs or chat; the key is read only on the server.
* **Kept by the app**: the ledger and the usage counter above, the enquiry the person approved (with its summary Brief), and ordinary CRM audit rows. **Not kept**: the pasted text, the prompt, the model output, any chat history.
* Real client briefs require the owner's separate approval (`docs/jarvis-setup.md`). Whether the provider retains data is governed by the owner's Anthropic agreement and settings: `Unverified` here.

## 8. Provider, limits and cost controls

Environment (server only; defaults in `lib/jarvis/config.ts`): `ANTHROPIC_API_KEY`, `JARVIS_MODEL` (default `claude-sonnet-5-5`), `JARVIS_MAX_INPUT_CHARS` (6000), `JARVIS_MAX_OUTPUT_TOKENS` (1200), `JARVIS_TIMEOUT_MS` (20000), `JARVIS_DAILY_LIMIT_PER_USER` (30, counted in the database so restarts and several instances do not reset it), `JARVIS_CONFIRMATION_SECRET`, `JARVIS_CONFIRMATION_TTL_MINUTES` (15), `JARVIS_DISABLED=1` (hard off), `JARVIS_PROVIDER` (`anthropic`, or `simulated` outside production). The **simulated provider** (`provider/simulated.ts`) is a deterministic stand-in for tests and local runs and is **refused when `NODE_ENV` or `VERCEL_ENV` is `production`** (the isolated local stack, a production build against a loopback database and no Vercel runtime, needs an explicit extra switch; `config.ts` `simulatedAllowed`; tested). A provider error, a timeout or a limit hit ends in a plain message that says Sales & CRM is not affected; the ordinary forms keep working.

## 9. Known gaps and what was not verified

* **Live provider**: no real AI call was made (tests and the walk-through use the simulated provider). The request shape of `provider/anthropic.ts` is tested against a mocked `fetch` only. A single live check is pending an owner-approved key (`docs/jarvis-setup.md`).
* **Hosted**: nothing applied; the migration, the pilot and the Vercel variables are owner steps (`docs/jarvis-deployment.md`). Hosted behaviour is `Unverified`.
* **The confirmation boundary is now enforced in the database** (section 6.1): the earlier caveat that a pilot person could call a wrapper directly with their own values no longer holds. What remains: a genuine proof proves that the server validated this exact action for this person, not that a human pressed the button (nothing short of a privileged proxy could prove that), and the proof key must be set by the owner and kept equal to `JARVIS_CONFIRMATION_SECRET` (a mismatch fails closed). Hosted behaviour is `Unverified`.
* The classifier is a deterministic keyword-and-verb list: it can miss a cleverly phrased request (the missing tool is the real wall) and, rarely, refuse a genuine brief that contains such a sentence (the person is told to remove it).
* Part 2 limits, stated plainly: *draft a reply* cannot know prices, dates or availability (they are not recorded in the enquiry as quotes; the draft flags every one it finds and says availability is unconfirmed); its scan is a pattern list (prices, dates, availability and promise wording) and can miss an unusual phrasing, so the person must still read the draft. *Help* answers only the 19 topics in `help/guidance.ts`; a question it has no topic for is told so. *Update* offers ten fields only; to change anything else use the enquiry page. *Change status* is one step at a time and never covers On hold, Won, Lost, reopen or handover (section 2.2). *Meeting notes* assigns the follow-up to the approver only and accepts a date only when the notes state it. *Register* sets no owner, lead source, exhibition or contacts. Projects, Inventory and People & HR still have no actions and no grant checker (`runtime.ts` returns false for them). No emails are sent, no existing organisation is changed, and JARVIS never marks Won, closes, reopens, hands over, deletes or changes access.
* The panel is English only; it was exercised with a mouse and keyboard in Chromium (desktop and a 390-pixel viewport), not on a real phone.

## 10. How the next module registers actions

1. Create `apps/web/src/lib/jarvis/<module>/<action>.ts` exporting a `JarvisActionDefinition` (`lib/jarvis/types.ts`): `id` = `jarvis.<module>.<noun>.<verb>`, `module`, `title`, `description`, `risk` (`read`, `draft`, `write`, `external`), `requires` (`moduleGrant`, optional `capability`), `status` (`enabled` or `disabled` with a reason), `usesProvider`, `inputSchema` and `valuesSchema` (zod; unknown keys dropped), `describe`, `propose(ctx, input)` (**never writes**; returns `{values, target, valid, card}`), optional `authorize` (the action's own rule rechecked at execution), `wirePayload(values, ctx)` (the exact object the wrapper receives; what the proof signs), `execute(ctx, {confirmationId, proof, values, target, acknowledgements})` (pass `proofRpcArgs(input.proof)` to the wrapper) and `verify`.
2. An action may touch **only its own module's data, through that module's own existing code paths and the person's own session** (`ctx.supabase`). No cross-module reads, no service-role client.
3. For a write that must not repeat, add a definer RPC in a **new** migration with the standard seven proof parameters (`p_confirmation, p_company, p_target, p_version, p_expires, p_mac, p_payload`) that **starts with `jarvis_verify_proof('<its own action id>', ...)`** (a wrapper without it is refused by the verify pack and the RLS tests), records the confirmation id in the ledger and calls the module's existing function in the same transaction (copy `jarvis_register_organisation`: after the proof it calls `jarvis_ledger_enter`, does the work in its own sub-block and ends with `jarvis_ledger_done` or `jarvis_ledger_fail`; a generic action returns `{resultId, reference, extra}` and a `resultView` so the panel and the read-only status call show the same result), with an owner pack. (JARVIS part 2 extended the unapplied part-1 migration in place instead.)
4. Register it in `lib/jarvis/actions.ts` and add the module's grant checker to `defaultJarvisDeps.moduleGrant` in `lib/jarvis/runtime.ts`.
5. Add tests (copy the structure of `create-from-brief.test.ts`: every-request authorisation, token tamper/expiry, injection, denied data not sent to the provider, logs; add the new wrapper to the `KINDS` table of `jarvis-proof.rls.test.ts` so the direct-call matrix covers it) and a catalogue entry.
