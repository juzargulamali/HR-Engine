## 1. What it is

One assistant for the whole app, with **one floating launcher on the right edge** of every signed-in page (`apps/web/src/components/jarvis/jarvis-launcher.tsx`, drawn from `apps/web/src/app/(app)/layout.tsx`). It is **OFF by default** and appears only for people the server says may use it (section 5). In part 1 it knows one capability, **Sales & CRM**, and one enabled action: turn a pasted brief into a **review card** for a new enquiry. **Nothing is saved until the person presses "Create enquiry"** on that card.

* Launcher: accessible name "Open JARVIS" (the words slide out on hover or keyboard focus; click, tap and Enter/Space all open it). Phone: a round button above the bottom bar. Original compact SVG mark (`jarvis-mark.tsx`): a geometric J that turns inward and ends in a small square; colour from the token `--jarvis-mark` (Enginious teal `#1D5D6C` in the light theme, cyan `#27CDD8` in the dark theme; `apps/web/src/app/os-design.css`); a brief pulse on opening, off for `prefers-reduced-motion`.
* Panel: title "JARVIS", subtitle "Enginious OS assistant", badge "Sales & CRM", first line "Paste a brief and I'll turn it into an enquiry for you to review." Desktop: a side panel (not modal, so the page stays usable while it is open). Phone: a full-height bottom sheet (modal, focus trapped). Escape closes it and focus returns to the launcher; opening moves focus to the message box.
* Context chips: the **active company** (a picker when the person may use JARVIS for more than one) and, on `/sales/opportunities/<id>` or the list's `?open=<id>`, the **enquiry** the page is about. This is a **hint, not permission**: the enquiry is re-read through the person's own session (`assistant.context`, `lib/jarvis/assistant.ts`); one the person cannot read is not revealed. If the route moves to an enquiry of another company the panel switches company **visibly** (a notice) and a review made for the other company can no longer be used; a review is bound to its company, so it is never retargeted silently.
* My Day is an entry point only: JARVIS does not copy its task list.
* **No persistent chat history.** The conversation lives in the panel component's memory; reloading the page clears it. The server stores only the action ledger and the daily usage counter (section 6). Test: `jarvis-launcher.test.tsx` ("stores nothing in the browser"), `create-from-brief.test.ts` (static scan: no storage, no file writes, no privileged client, no direct table writes).

## 3. How "create an enquiry from a brief" works

1. **Paste** a WhatsApp message, email or rough brief (limit `JARVIS_MAX_INPUT_CHARS`, default 6000).
2. **Refusal list first** (`lib/jarvis/classifier.ts`): a request for payroll, salaries, leave, other modules' records, raw SQL, source code, credentials, configuration, deployment, permission changes, or deletion of records or audit history is refused **before** any provider call or usage count. It looks for a request (a verb aimed at the thing), not the word, so "a payroll company's gala" passes. It is defence in depth: the wall is that no such action exists and the database permissions apply whatever the text says.
3. **Extraction** (`provider/`): the provider receives **only** the pasted text, fixed instructions and the field schema (one forced tool, `record_fields`). The model returns a plain object; the server prunes it to the known keys, length-limits every string and blanks every invalid value (`sales/extraction.ts`). Anything else it returns (an "execute" flag, a company id, an organisation id, an owner, a role) is dropped. **Organisation names are search texts only; ids are never taken from the model.**
4. **Fields**: exactly the existing create-enquiry form's (`createOpportunitySchema`, `apps/web/src/lib/actions/crm.ts:63`; `sales-enquiries.md` section 3): title, source (the 8 fixed options), agency, end client, currency, value, budget note, brief, event start and end, installation, location, technologies (name and whole quantity), scope, waiting on, next action (title, due date, time 10:00 Dubai, type). Unknown optional fields stay **blank**. Owner is always the approving person (the form's default); contacts are linked on the enquiry page afterwards. The enquiry's Brief field holds a short **summary**, not the pasted text.
5. **Agency versus end client** (the Clients & Agencies role model, `sales-clients-and-agencies.md` section 9.2): an organisation is offered for a field only if it carries that role (`lib/crm/organisation-roles.ts`). One exact match with the right role is selected; a partial or ambiguous match is a **question** with options; an organisation that exists without the role says so; one that does not exist says "Register it in Clients & Agencies first". **JARVIS never creates an organisation** (`jarvis.sales.organisation.register` is disabled). The look-ups run through the person's own session (RLS) and return only id, name and place.
6. **Duplicates** (`sales/duplicates.ts`): the same deterministic rules as the form (`crm_find_duplicate_candidates` + `findLikelyDuplicates`, `packages/domain/src/crmDuplicates.ts`), limited to the **selected company**. A "likely" duplicate must be acknowledged on the card ("These are not the same enquiry") and is **re-checked at execution**; a check that fails fails closed.
7. **Clarifying questions** appear on the card (missing title, source, next action, date; ambiguous organisation); the person answers by filling the field or picking an option and presses "Review changes" (a revise call: no provider call, no usage). Required fields and rules are those of the form and the database (next-action date not before today in Dubai; show end not before start).
8. **Review card** (`review-card.tsx`): editable fields, the exact company, linked organisations, duplicates, what is still missing. **"Create enquiry" is enabled only when** the card is complete and valid, unchanged since its review, for the current company, and any likely duplicate was acknowledged.
9. **Create**: the explicit button calls the one write endpoint (`jarvisConfirm`, `apps/web/src/lib/actions/jarvis.ts`). The result shows the **real reference** (`OPP-<code>-<year>-<nnnn>`) and a link **only after** the app has read the enquiry back through the person's own session (`verify`). An unknown answer shows "Checking the original result" (a read-only status call by confirmation id) and **never offers a second create**.

## 5. Access: never broader than the person's own permissions

Checked **on every request** (propose, review, confirm, status, context), in this order (`createDispatcher.authorize`, `apps/web/src/lib/jarvis/dispatcher.ts:48`):

1. the environment: `JARVIS_DISABLED`, a configured provider (key, or the simulated one outside production), and in production `JARVIS_CONFIRMATION_SECRET`; any failure = "unavailable" and ordinary CRM is unaffected;
2. the **authenticated session** (`supabase.auth.getUser()`); no user id, company, flag or role is read from the browser;
3. the database controls through `jarvis_my_access(company)`: the **global switch** (`enabled`), the **pilot allowlist** (`jarvis_pilot_users`), the **write kill switch** (`writes_enabled`; without it read-only help keeps working but creating is refused) and the optional **company list** (`jarvis_pilot_companies`; empty = no company restriction);
4. the **module grant for the selected company** (an active Sales grant), then the action's own rule and the records' visibility (RLS) inside the action.

**Hiding the launcher is not access control**: the layout asks the same server (`lib/jarvis/launcher.ts`) only to decide whether to draw it; every call re-checks. A pilot person with no Sales grant gets no launcher and, if they call the server actions directly, a refusal. Access revoked between the review and the click is refused (`create-from-brief.test.ts`, `jarvis-flow.mjs`).

**Hard exclusions, regardless of the person's other roles:** JARVIS has no tool for salaries, leave, payroll, other modules' records, raw SQL, source code, credentials, application configuration, deployments, permission changes, or deletion of records or audit history. The registry is deny by default (`lib/jarvis/registry.ts`): an id that is not registered and enabled is refused as unknown; the classifier refuses such requests before the provider; if one reached the model the model has no tool for it and the server would not execute it.

## 6. Confirmation, retries and what is stored

* **Server-bound confirmation.** `propose` never writes. When the card is valid it returns a **confirmation token** signed with HMAC-SHA256 (`JARVIS_CONFIRMATION_SECRET`; `lib/jarvis/token.ts`) binding: the authenticated user id, the company id, the action id, the target (`new`, or a record id and version for later actions), the SHA-256 of the **canonical form of the exact reviewed values** (`canonical.ts`), the confirmation id and an expiry (`JARVIS_CONFIRMATION_TTL_MINUTES`, default 15). `jarvisConfirm` takes only the token plus the reviewed values; the server verifies the signature, expiry, user, action and company, recomputes the hash and **rejects** tampered, expired, wrong-user, wrong-company, wrong-action or edited confirmations, rechecks authorisation and the organisations, and asks for a fresh review when anything differs. **A chat message such as "confirmed" never executes anything**: it is just another brief; only the card's button calls the write endpoint. (Stale record **versions** are part of the token for later update actions; part 1 creates new records only, so `ver` is null.)
* **Idempotency.** The ledger `jarvis_action_ledger` has a **unique confirmation id**. `jarvis_create_enquiry` takes an advisory lock on it, inserts the ledger row and creates the enquiry in **one database transaction**; a repeat returns the **original** result and creates nothing; N concurrent calls create exactly one (RLS test: 12 in parallel). A used confirmation id with a different person, company or reviewed values is refused. A refusal by the existing rules (for example a missing agency role) is recorded once as `failed`, creates nothing, consumes no reference number, and is replayed on a repeat: a failed confirmation is final, the person reviews again.
* **Timeouts and restarts.** The ambiguous case (network error or timeout, or a save that could not be read back) shows "Checking the original result": the panel polls the read-only `jarvisStatus` by confirmation id (the person's own ledger row). A simulated server restart between propose and execute still works (the token is stateless and the ledger is durable): tested in `create-from-brief.test.ts`.
* **What is stored.** `jarvis_action_ledger`: confirmation id, user, company, action id, target (`new`), the hash of the reviewed values, status, the created enquiry's id and reference, an error code and message from the database's own refusal text, timestamps. **No brief, email body, prompt, model output or secret.** `jarvis_usage`: requests per person per Dubai day. Plus the usual CRM timeline: the new enquiry gets its ordinary "Enquiry created." event and a second event "Enquiry created through JARVIS ..." whose actor is the approving person (`helpers.ts` `describeEvent`).
* **Logs.** `lib/jarvis/log.ts` accepts only short identifier-like fields (event, action id, outcome code, provider kind, duration); text is dropped. Test: a full flow with a marker string and a payroll request logs none of the brief, names, token or ids.

## 7. Data that leaves Enginious OS, and what the app keeps

* **To the AI provider** (Anthropic Messages API, `provider/anthropic.ts`, server side only): the **pasted text** the person sends, the fixed instructions, today's date and the field schema. **Nothing else**: no enquiries, no organisations, no ids, no company data, no other module, no tool list of other modules. Candidate organisations from look-ups stay in Enginious OS (they are shown to the person; they are not sent to the model). A test asserts the exact request keys and that no record, organisation or id appears in them (`create-from-brief.test.ts`, "denied data never reaches the provider").
* **Never**: the API key to the browser, Git, logs or chat; the key is read only on the server.
* **Kept by the app**: the ledger and the usage counter above, the enquiry the person approved (with its summary Brief), and ordinary CRM audit rows. **Not kept**: the pasted text, the prompt, the model output, any chat history.
* Real client briefs require the owner's separate approval (`docs/jarvis-setup.md`). Whether the provider retains data is governed by the owner's Anthropic agreement and settings: `Unverified` here.

## 8. Provider, limits and cost controls

Environment (server only; defaults in `lib/jarvis/config.ts`): `ANTHROPIC_API_KEY`, `JARVIS_MODEL` (default `claude-sonnet-5-5`), `JARVIS_MAX_INPUT_CHARS` (6000), `JARVIS_MAX_OUTPUT_TOKENS` (1200), `JARVIS_TIMEOUT_MS` (20000), `JARVIS_DAILY_LIMIT_PER_USER` (30, counted in the database so restarts and several instances do not reset it), `JARVIS_CONFIRMATION_SECRET`, `JARVIS_CONFIRMATION_TTL_MINUTES` (15), `JARVIS_DISABLED=1` (hard off), `JARVIS_PROVIDER` (`anthropic`, or `simulated` outside production). The **simulated provider** (`provider/simulated.ts`) is a deterministic stand-in for tests and local runs and is **refused when `NODE_ENV` or `VERCEL_ENV` is `production`** (the isolated local stack, a production build against a loopback database and no Vercel runtime, needs an explicit extra switch; `config.ts` `simulatedAllowed`; tested). A provider error, a timeout or a limit hit ends in a plain message that says Sales & CRM is not affected; the ordinary forms keep working.

## 9. Known gaps and what was not verified

* **Live provider**: no real AI call was made (tests and the walk-through use the simulated provider). The request shape of `provider/anthropic.ts` is tested against a mocked `fetch` only. A single live check is pending an owner-approved key (`docs/jarvis-setup.md`).
* **Hosted**: nothing applied; the migration, the pilot and the Vercel variables are owner steps (`docs/jarvis-deployment.md`). Hosted behaviour is `Unverified`.
* The confirmation token is an **application** control: its HMAC cannot be verified inside the database. A pilot person with a browser session could call `jarvis_create_enquiry` directly with any values; that gives them nothing they cannot already do by calling `crm_create_opportunity` themselves (same identity, same rules), but the "reviewed values" guarantee holds only through the app.
* The classifier is a deterministic keyword-and-verb list: it can miss a cleverly phrased request (the missing tool is the real wall) and, rarely, refuse a genuine brief that contains such a sentence (the person is told to remove it).
* One enabled action only. The Projects, Inventory and People & HR modules have no actions and no grant checker (`runtime.ts` returns false for them). No emails are sent, no organisations are created, no existing enquiry is changed by JARVIS.
* The panel is English only; it was exercised with a mouse and keyboard in Chromium (desktop and a 390-pixel viewport), not on a real phone.

## 10. How the next module registers actions

1. Create `apps/web/src/lib/jarvis/<module>/<action>.ts` exporting a `JarvisActionDefinition` (`lib/jarvis/types.ts`): `id` = `jarvis.<module>.<noun>.<verb>`, `module`, `title`, `description`, `risk` (`read`, `draft`, `write`, `external`), `requires` (`moduleGrant`, optional `capability`), `status` (`enabled` or `disabled` with a reason), `usesProvider`, `inputSchema` and `valuesSchema` (zod; unknown keys dropped), `describe`, `propose(ctx, input)` (**never writes**; returns `{values, target, valid, card}`), optional `authorize` (the action's own rule rechecked at execution), `execute(ctx, {confirmationId, valuesHash, values, target, acknowledgements})` and `verify`.
2. An action may touch **only its own module's data, through that module's own existing code paths and the person's own session** (`ctx.supabase`). No cross-module reads, no service-role client.
3. For a write that must not repeat, add a definer RPC in a **new** migration that records the confirmation id in the ledger and calls the module's existing function in the same transaction (copy `jarvis_create_enquiry`), with an owner pack.
4. Register it in `lib/jarvis/actions.ts` and add the module's grant checker to `defaultJarvisDeps.moduleGrant` in `lib/jarvis/runtime.ts`.
5. Add tests (copy the structure of `create-from-brief.test.ts`: every-request authorisation, token tamper/expiry, injection, denied data not sent to the provider, logs) and a catalogue entry.
