# Projects & Tasks action catalogue

Status: built from the code on the Projects & Tasks Phase 1 branch `claude/admiring-cray-uky379` (merged as PR #82 (merge `30c7895adc75f834a60b00ed3bca7015b1654282`, 2026-11-11)). **Code read only; nothing was run to produce it.** One row per action that changes data: the permission and where it is enforced, the starting state, the server action and database function, the records changed, the resulting state, who is notified and whether a repeat is safe. Assembled from the `## Actions` table at the end of each reference file ([coverage index](./projects-coverage-index.md)); a point a reference could not confirm reads `Unverified` in its row.

## 0. What this catalogue is NOT (read first)

* **Availability as a UI action does not make something an approved tool for an AI worker.** A button existing only means a person can press it. JARVIS has no Projects actions and reads no Projects data: documenting a workflow here gives it guidance content only; a new action or data access needs its own implementation and approval (`jarvis-rulebook.md`).
* **A documented database function is NOT automatically an approved tool.** Every function named here is reached through an app server action with the signed-in person's own session. Nothing in this file authorises calling a function directly, from SQL, or with a service key.
* Internal helpers, triggers and scheduled functions are not listed as actions (for Chat: `chat_is_member`, `chat_is_project_member`, `chat_ensure_project_group`, `chat_import_project_messages`, the mirror triggers). No worker should call them.
* Hosted data: this describes the code. It says nothing about hosted records (`CLAUDE.md` boundaries).

## 1. Rules that hold across the module

1. **The database decides.** Each function checks the caller again (`proj_can_manage`, `proj_is_active_member`, `proj_has_capability`, the task role rules in `packages/domain/src`); a screen hiding a control is a convenience.
2. **Read before write.** Where a row below names a version check, a stale save is refused and the person is told to reload. Where it says there is none, a concurrent change is not detected.
3. **Retry.** The last column says whether repeating the action is safe. Treat "not safe" literally: a second press creates a second record.
4. **Finished projects** (completed or archived) are read-only on the screens; the rows note where the function itself does not check this.
5. **Notifications** are in-app project notices (`proj_notify`, listed on My Work); nothing here sends email or leaves the system.

## 2. End-to-end order (the workflow these actions form)

Sales marks the enquiry won and submits the handover (`sales-action-catalogue.md`, `sales-close-and-handover.md`) -> `projects.handover.assign_pm` -> `projects.handover.accept` (project created; the Project Manager lands on Work) -> `projects.member.add` (which also puts the person in the project's Chat group, with no separate step) -> `projects.task.create`, the status moves and review -> the Delivery Plan (`projects.plan.*`: deliverables and their breakdown, then `projects.plan.release`, which creates the tasks and adds hardware to the draft equipment request) -> `projects.equipment.*` (draft from the handover and the plan, review, submit; the warehouse reserves, dispatches and later receives back in Inventory) -> `projects.project.complete` (does **not** return equipment) -> returns recorded by the warehouse, the return note acknowledged. The step-by-step trace with screens, buttons and who is told is in [`projects-handovers-equipment-and-workflow.md`](./projects-handovers-equipment-and-workflow.md) section 4.

## 9. Membership and the Chat group (not actions of their own)

There is no "add to chat" or "remove from chat" action. Old Discussion links (`/projects/<id>/discussion`) send a member to `/projects/<id>/work?chat=<group>`; anyone else is shown no conversation.
