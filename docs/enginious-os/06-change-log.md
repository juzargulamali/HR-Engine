### 2026-11-09 | JARVIS: the review token is split from the database proof; the duplicate acknowledgement is signed and enforced in SQL | branch `feat/jarvis` (draft PR #70, kept in draft); **hosted: NOT applied; nothing enabled in Production; no live AI provider called; no service-role key or privileged proxy anywhere**
* The problem: after the previous fix, `propose` returned to the browser the very MAC the database accepts as execution proof (`jarvis_verify_proof`, domain `JARVIS-PROOF-V1`), so any eligible pilot person could take the proposal's token and call a write wrapper directly, without the explicit confirmation request ever happening. Also the organisation wrapper's duplicate acknowledgement `p_ack` was outside the signed material.
* The fix: **two distinct artefacts from one secret.** The **review token** (proposal time, held by the browser) is made with `review_key = HMAC-SHA256(secret, "JARVIS-REVIEW-KEY-V1")` over a text starting `JARVIS-REVIEW-V1` (person, company, action, target, version, expiry, the confirmation id (jti) and the hash of the exact reviewed values) and is verified only by the app server; the database never has the review key. The **database proof** is made with `proof_key = HMAC-SHA256(secret, "JARVIS-PROOF-KEY-V1")` over `JARVIS-PROOF-V1`, **issued server-side only inside the explicit confirmation request** after the review token (signature, expiry, user, company, action) is verified, access is rechecked as on every request, and the hash of the values actually submitted equals the one the token bound; it carries the SAME jti and lives `JARVIS_PROOF_TTL_SECONDS` (default 120) and is **never returned, logged, stored or put in a URL or response**. `jarvis_set_proof_key(secret)` derives the proof key inside the database and stores only it (the root secret and the review key are not stored); owner step and rotation are unchanged (one value, DB and env together). Retries after a timeout re-run the confirmation with the same review token: a fresh proof, the same jti, the ledger returns the original result.
* The acknowledgement: `p_ack` is removed (every wrapper now takes exactly the seven signed arguments). The server rechecks duplicates and requires the acknowledgement to equal the current same-name or same-website matches, then signs `acknowledged_org_ids` into the payload text; `jarvis_register_organisation` reads it only from the verified payload and **the database itself** requires it to equal the organisations `crm_import_candidates` finds at execution time (omitted, changed, extra, a proof for another acknowledgement or a duplicate that appeared after the review: refused, nothing written, no ledger row). The audit of the other four wrappers found no other unsigned parameter that affects a write (`jarvis_usage_take(limit)` is bookkeeping on the caller's own counter only).
* Shared vectors (`supabase/tests/jarvis-proof-vectors.json`) now cover both derivations and both artefacts. Tests: RLS `jarvis-proof.rls.test.ts` (direct calls by an eligible pilot person to each of the five wrappers: the review token as the MAC in many arrangements and wrong key/domain combinations; the acknowledgement omitted, changed, extra, signed differently, appearing after review, correct, retried; every earlier case on the new flow); web tests (no string in the propose response verifies as a database proof; the proof is issued only after re-verification; tampered, expired, wrong-user/company/action, changed-value, revoked-access and stale-record cases cause no write RPC; no proof in any response, log or client file; a timeout retry reuses the jti and returns the original). ### 2026-11-09 | JARVIS confirmation boundary: every write verifies a server-issued proof inside the database | branch `feat/jarvis` (draft PR #70); **hosted: NOT applied; nothing enabled in Production; no live AI provider called; no service-role key or privileged proxy anywhere**
* *Superseded in part by the entry above (the token returned at proposal is now a review token; the database proof is issued server-side only; `p_ack` is gone).* The defect: the confirmation token was verified only in the app server, so an eligible pilot person could call any JARVIS write wrapper (`jarvis_create_enquiry`, `jarvis_register_organisation`, `jarvis_update_enquiry`, `jarvis_change_stage`, `jarvis_record_meeting`) straight through the platform API with a confirmation id and hash they invented, and write something nobody reviewed. A caller-supplied id and hash are not proof.
* The fix (migration `20261223000100_jarvis_platform.sql` edited in place, never applied on hosted; `modules/jarvis.md` section 6.1): every wrapper's first statement is `jarvis_verify_proof`, which recomputes an HMAC-SHA256 over format version, the approving person (`auth.uid()`), company, the wrapper's own hard-coded action id, target, record version (or "-"), expiry, a unique proof id and the SHA-256 of the exact payload text, with a key only the database's own functions can read (`jarvis_proof_key`: RLS on, no policy, no privilege for `public`, `anon`, `authenticated` or `service_role`; set by the owner with `jarvis_set_proof_key`, the same value as `JARVIS_CONFIRMATION_SECRET`; no key = every wrapper fails closed), compares in constant-time style and judges expiry by the DATABASE clock. Only then does a wrapper take the lock, write the ledger row and call the existing function (permission checks inside unchanged, atomic write + ledger and idempotency preserved). A refused proof writes nothing (no record, no ledger row, no timeline event). Versioned wrappers (update, change status) also require the signed version to still be current (40001, nothing written; before, a stale version left a `failed` ledger row). The MAC is HMAC-SHA256 in plpgsql on the built-in `sha256(bytea)` (no `pgcrypto`), proved equal to Node's `createHmac` on shared vectors (`supabase/tests/jarvis-proof-vectors.json`). The wrappers' signatures changed (`p_confirmation, p_company, p_target, p_version, p_expires, p_mac, p_payload`; the organisation wrapper also takes the unsigned `p_ack`); the old signatures are dropped by the migration and by the rollback.
* App: `lib/jarvis/token.ts` issues the proof (the token IS the MAC proof, still verified in the app first), each action gains `wirePayload` (the exact object the wrapper receives; canonical JSON text is what is signed and sent byte for byte), `execute` passes `proofRpcArgs(input.proof)`; an edited value gives a new payload hash and needs a new review and a NEW proof; replay by confirmation id, the read-only status call and the user-facing refusals are unchanged (new plain messages for a database refusal of the proof).
* Owner pack and docs: `jarvis_00` (checks `sha256`, no key table yet), `jarvis_05` (six tables and fourteen functions intended to change), `jarvis_20` (key table closed to every API role and without a policy, signed-in users can execute exactly seven `jarvis_*` functions, each wrapper verifies the proof with its own action id before any lock or write, key "set / not set" only), `jarvis_90` (drops the key table and functions; removes the stored key); `docs/jarvis-deployment.md` new OWNER STEP and rotation, `docs/jarvis-setup.md` (the env secret and the database key must match), `modules/jarvis.md` 6.1 (what is signed, where verified, what a direct caller can and cannot do, the wrapper audit table; the old caveat is removed), catalogue retry fields, `03` access row.
