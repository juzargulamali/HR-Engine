# Launch correctness package 1b: manual database steps

**Nothing here has been run on any hosted project.** Each section below is one database change from the launch correctness work. Each is applied by you, in the Supabase SQL Editor of **Enginious HR Engine_V2**, when you decide to; each can be reviewed, applied, paused or rolled back on its own. The application changes that go with them need no SQL. Run each file, paste the **whole** result back, and wait for a reply before the next step. No step writes data: the migrations replace functions only.

**Installation order for the whole stack: `docs/launch-refinement-install-order.md` (one list, 14 migrations, `20261216000100` to `20261217000100`; packages 1 then 2 then 3).** This guide covers #1 and #2 of that list.

## A7. Employee equipment: reserve, then issue (`20261216000100_inv_issue_to_employee_consumes_reservation.sql`)

**The defect (reproduced on a local copy before the fix).** The request workspace tells the warehouse to *Reserve*, then give the equipment. Issuing a reserved unit to the employee against the same request was refused with "is reserved for *that very request*"; for counted stock the request's own reservation was subtracted from what could be issued, and the reservation was never marked as issued, so Today kept saying "ready to send".

**What the migration does.** Replaces one function, `inv_issue_to_employee`, in place (`create or replace`). No table, column, policy or privilege changes; no data changes. When the issue is made against a request: a unit or quantity reserved for **that** request is consumed (its dispatched quantity goes up exactly as in a project dispatch); a unit or quantity reserved for **another** request is still refused with the same message; stock beyond what the request reserved must still be unreserved stock on the shelf. A reservation issued in full is marked completed, because nothing tracks an employee's equipment back through reservations and an active one would keep the unit blocked after it was returned. An issue with no request behaves exactly as before. Who may issue, idempotent replay, booking conflicts and the append-only movement history are unchanged.

1. **Preflight (read-only).** `supabase/manual-sql/inv_emp_issue_00_preflight_readonly.sql`. Section B must say `OK` on every row and *not applied yet*. Section D is information (open employee requests and their active reservations).
2. **Snapshot (read-only).** `supabase/manual-sql/inv_emp_issue_05_preservation_check_readonly.sql`, exactly as it is. Keep the whole `paste` column.
3. **Apply.** Paste `supabase/migrations/20261216000100_inv_issue_to_employee_consumes_reservation.sql` into the SQL Editor and run it once (safe to run twice).
4. **Verify (read-only).** `supabase/manual-sql/inv_emp_issue_20_verify_readonly.sql`. The last row must say `OK … 0 failing` (14 checks: function present, security definer with a fixed search path, callable by signed-in users and not by anonymous visitors, the new rule present, every earlier refusal still present).
5. **Preservation compare (read-only).** Paste the step 2 lines where the comment says `>>> PASTE <<<` and run the same file again. The summary must start with **PASS**: nothing else in the schema changed, the reservation, movement, request, unit and balance tables are identical, and the function is the new version with the same privileges.
6. **Try it once in the application.** Open an employee request that has a unit reserved, issue that unit against the request: it is accepted, the request line shows it as issued, and Today no longer lists it as ready to send.

Tested locally (a throwaway database from every migration): the failing reproduction before the fix and its passing after (`packages/rls-tests/test/inventory_employee_reserve_issue.rls.test.ts`), the whole Inventory test suite, and the four scripts above including the rollback (the rollback restores the exact earlier definition, shown by fingerprint). **Rollback:** `supabase/manual-sql/inv_emp_issue_90_rollback.sql` (read its header first: going back re-opens the defect; nothing issued or consumed is undone).

## A11. Scope change proposals tell the people who decide (`20261216000200_proj_scope_proposal_notifies_deciders.sql`)

**The gap.** When a Project Manager proposed a scope change, nobody was told. The people who decide (a Projects founder, or someone a founder gave scope approval) found it only by opening the project's *Feedback & changes* page. (The same applied to a commercial approval request in Sales; that one needs no database change and is handled in the application: Sales founders now see a *Commercial approval waiting for your decision* row on My Day.)

**What the migration does.** Replaces one function, `proj_propose_scope_change`, in place (`create or replace`). No table, column, policy or privilege changes; no data changes. After a proposal, each active founder and each `approve_scope` holder of the project's company **who can open the project** (a founder, or an eligible member: the existing notice rule) gets a notice, once per proposal; the proposer is never told. My Day shows a *Scope change waiting for your decision* row from the proposal itself, so it disappears when the change is approved, rejected or withdrawn. Who may propose, who decides, the cost effect (still restricted) and the decision function are unchanged.

**What was checked first (runtime, on a local copy).** A holder of `approve_scope` who is **neither a founder nor a member of the project** can still decide if they call the function, but cannot read the proposal (row-level security needs founder or membership) and cannot open the page. They are **not** given a notice, because there is nothing they could open, and this change creates no new access for them. If you want such people to be able to read and decide, that widens who can read scope changes: it is your decision, and it is not made here. The preflight lists any such people on the hosted system (read-only) so you can see whether the situation exists. **Follow-up:** the completion pass lets such a holder open and decide the proposal through a narrow page that shows only the proposal itself (title, proposed scope, effect on dates, proposer), without making them a member; see `docs/launch-p1d-deployment.md`.

1. **Preflight (read-only).** `supabase/manual-sql/proj_scope_notify_00_preflight_readonly.sql`. Section B must say `OK` and *not applied yet*. Section D shows how many proposals wait today and, **read-only, who holds `approve_scope` without being a founder**, and whether each is a member of a project (the row ends *NOT a member of any project* for those who could not open a proposal).
2. **Snapshot (read-only).** `supabase/manual-sql/proj_scope_notify_05_preservation_check_readonly.sql`, exactly as it is. Keep the whole `paste` column.
3. **Apply.** Paste `supabase/migrations/20261216000200_proj_scope_proposal_notifies_deciders.sql` into the SQL Editor and run it once (safe to run twice).
4. **Verify (read-only).** `supabase/manual-sql/proj_scope_notify_20_verify_readonly.sql`: the last row must say `OK … 0 failing` (11 checks: privileges, the notice rule, and every earlier refusal still present).
5. **Preservation compare (read-only).** Paste the step 2 lines where the comment says `>>> PASTE <<<` and run the same file again. The summary must start with **PASS**: nothing else changed; scope changes, their restricted cost table, grants and notices are identical.
6. **Try it once.** A Project Manager proposes a change on a test project: a founder (or a member holding scope approval) sees the row on My Day and, in *My work*, the notice.

Tested locally: the failing reproduction before the fix and its passing after (`packages/rls-tests/test/project_scope_decider.rls.test.ts`, which also records the runtime finding and that a member without the right is still refused when calling the decision function directly), the Projects test suite, and the five scripts above including the rollback (the rollback restores the exact earlier definition, shown by fingerprint). **Rollback:** `supabase/manual-sql/proj_scope_notify_90_rollback.sql` (going back means a proposal tells nobody again; notices already written stay).
