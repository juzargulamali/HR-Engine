# Launch refinement: the one installation order (packages 1, 2 and 3)

**Nothing in this stack is a hosted action until the owner runs it; Claude has run none of it on any hosted project. The owner's own hosted runs and results are recorded, as the owner reported them, in section 5.** This page is the single authoritative list of the 15 database changes and the sequence for them, the four pull requests and the optional notes switch. **Migrations 1 to 15 are installed and verified on V2, as reported by the owner (section 5).** The package guides (`docs/launch-p1b-deployment.md`, `launch-p1c`, `launch-p1d`, and `launch-p2` / `launch-p3` on #54 / #55; `docs/inventory-cross-company-receiving.md` for #15) explain each change and link here; if a guide and this page differ, this page wins and the guide is a bug.

**Fast route for the later twelve (3 to 14): the batch.** When migrations 1 and 2 are already applied, `docs/launch-batch-install.md` installs 3 to 14 in three owner runs instead of the per-migration loop in section 2: `launch_batch_00_preflight_and_snapshot_readonly.sql` (read-only), `launch_batch_20_install_3_to_14.sql` (changes the database, one all-or-nothing transaction) and `launch_batch_90_verify_and_compare_readonly.sql` (read-only), all in `supabase/manual-sql/`. It contains exactly the SQL of the migrations listed in section 3, in the same order (generated by `scripts/build-launch-batch.mjs` and checked byte for byte by `npm run check:launch-batch`); nothing about the order, the table below or the other rules changes, and the per-change packs stay available for troubleshooting and for rolling a change back. **The batch covers 3 to 14 only and is not changed: #15 is installed on its own with its own pack (`inv_xshare_*`), after 1 to 14 are verified.**

## 2. The sequence

Every one of the 15 changes was checked against the **current `main` code** (before any of the four pull requests): **none breaks it**, so the database changes can go first and the old application keeps working while they are applied (section 3, column A). Several new screens do need the new functions (column B), which is why the database goes first.

1. **Baseline (once, before anything).** Record the Vercel cron run history and the PostgreSQL `pg_cron` job list and history as two separate records (`docs/launch-refinement-hosted-checklist.md`). Nothing in this stack activates or changes either scheduler.
2. **Database: apply migrations 1 to 15 in file-name order** (the timestamps sort in install order across all four packages; 1 to 14 are already installed on V2, so only #15 remains). The one hard dependency is **#9 needs #3** (`user_is_active`): applying #9 before #3 would break approval routing for new requests, so never reorder it. A migration may be skipped only when the module it belongs to is not in use (column "Needs"). For **each** migration, in the SQL Editor of the V2 project, in this order: preflight (`_00`, section B says "not applied yet"), snapshot (`_05`, keep the `paste` column), apply the migration once, verify (`_20`, last row `OK … 0 failing`), compare (`_05` again with the pasted lines, summary starts `PASS`). Stop at the first row that is not as stated and send the whole result. The checklist's "expected before" findings (an existing defect shown by a preflight) are not a failed installation.
3. **Application: merge #53, then #54, then #55, then #56** (each is based on the one before it; after a merge, retarget the next pull request to `main` and let CI pass before merging it). Vercel deploys `main`. After each merge, run that package's rows of the hosted checklist. If the database changes of a package are not yet applied when its application is released, the new screens say they could not load that part (they never show an empty list or a zero): safe, but noisy, which is why step 2 comes first. Releasing in steps is also safe: apply 1 to 11 then merge #53; apply 12 and 13 then merge #54; apply 14 then merge #55; apply 15 then merge #56.
4. **The notes switch stays OFF** during installation and verification. Switching dispatch and return notes on (`inv_notes_30`) is a **separate, later owner decision**, made after #14 is verified and not as part of this installation; `inv_notes_80` switches it off again and is the first response to any note problem. With the switch off the dispatch and return functions behave as before, the note screens show nothing, and there is **no hosted verification of the new dispatch / return workflow in this release** (previews use the live V2 database, so nothing is written there).

Rollback, if ever needed: the pack's `_90_rollback.sql`, in the reverse of the order above (for example #9 before #3: rolling #3 back restores the older routing functions and would also undo #9's change).
